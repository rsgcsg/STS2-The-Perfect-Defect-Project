# SpireAgent 工程协作规则

适用于工程师、架构师、各级主管和 Agent；AI 特有事项见 [AI_COLLABORATION](AI_COLLABORATION.md)。本文件拥有日常工作方式，替代历史交接中的派工习惯，不覆盖用户最新指示、组件合同或实际权限。目标是交付有用结果、出错可定位，保持个人游戏项目需要的秩序；不建立银行级流程或新的管理平台。

## 1. 为什么做这个项目

近期：让 P1 环境、独立环境记录与转换、完整 Agent 接入、真实游戏与 Managed 对照形成可用且可复验的链。当前还未全部验收；准确状态见 [CURRENT](memory/CURRENT.md)，不能从设计文档推断已实现。
长期：做出有实际策略能力的 STS2 Agent，并能替换环境实现、协议、数据格式、模型与训练方法，而不反复重造控制、存储和用户入口。数据和平台工程服务这个目标，不是无限的前置工程。

STS2 拥有规则和原生执行；Connector 提供合法信息、完整有限动作与执行时复验；Host 管进程和隔离；Annotator/Evidence 管来源记录和验证；Runtime 管受控执行；应用管产品入口；研究管策略、模型、训练和评测。详见 [组件](COMPONENTS.md)。这是责任划分，不要求每层都新建服务。

## 2. 每次只承诺一个可验收结果

主管与执行者在动手前共同回答：**为谁解决什么问题、交付什么、怎样验、做到哪里停**。答案放在一个现有任务/issue/PR，CURRENT 只链接它；小任务几行即可，不同时填多个表。

最小任务卡：

| 内容 | 必须说清 |
|---|---|
| 目的与产物 | 当前用户能力/真实问题，下一位使用者，具体输出；不是“完善架构”“继续审计” |
| 范围与基线 | 一个负责人、版本/分支、可写范围；明确本次不做什么；跨组件可属于同一因果修复 |
| 验收 | 成功行为和必要反例、最低可信检查；代码/运行/策略质量分别需要什么证据 |
| 资源与决定 | 已授权动作，时间检查点、昂贵测试/游戏/费用上限，真实未知及谁决定 |
| 停止与返回 | 达标即交付；不可达时交实际成果、原失败和阻塞；下一任务是待派发，不自动开工 |

正常流程：有限调查 → 最短真实消费者路径或忠实反例 → 原 owner 实现 → 相关验证 → 一次适当审查 → 可用增量交付。新能力不必等发生事故才做；发现问题也不自动获得修复整个子系统的任务。
源代码子任务可完成，但父能力继续标未完成。不能用完成若干文件/测试替代任务原验收，也不能以“还有很多可完善的地方”拒绝结束。

## 3. 主管、架构师与执行者各自负责什么

- 主管拥有工作队列和取舍：通常一条主交付线，总在制主题不超过3个；这是上限，不是要填满的名额。每位执行者一次一个有界结果。审查与修复可属于同一主题。
- 主管先解开共享合同/接口依赖，再并行可独立验收的工作；不让多位作者各猜一种接口，也不把同一耦合修复切成很多微任务来增加交接。
- 架构师必须给出当前真实用例、受影响消费者、有限选项及迁移成本；不为假想扩展建设通用框架。架构意见不能无限增加下级验收条件。
- 执行者对真实改动和验证负责；发现范围外问题，给原证据和影响，放入现有待办，不顺手一路修下去。
- 负责人必须亲核关键 diff 和原结果，不能只接受子任务摘要；也不必把每个已验结论重新做一遍。责任不能因委派而转移。
- 已授权的内部沟通由参与者直接完成，不让用户充当转发器。没有实际工具访问/消息授权就说明限制，不虚构已发送或已派发。

## 4. 防止迷失与无限投入

每个任务给一个合理成本窗口，按风险和实际运行时长确定，不统一要求所有工作在固定分钟内完成。普通调查可先用10–20分钟、一个实现片段可先用60–120分钟作检查点；它们不是停止正确工作的硬期限或验收通过条件。

出现以下信号时，负责人必须重新判断，而不是原样续跑：
- 执行者说不清当前目的、用户价值或停止条件；
- 约定检查点到了仍没有新增事实、可用增量或减少一个关键不确定性；
- 同一失败反复重跑，没有新解释/新检测；
- 不断添加前置工作、审计或“安全证明”，却没有接近消费者；
- 新发现把任务变成多个主题，或不同文档开始派发不同主线。

恢复方法：用现有原件回到任务卡，判断目标/拆分/方法是否错误；选择继续当前有证据的方法、缩小本次交付、替换方法或停止这项无效工作。记录实际未完成项，不重命名为成功。不通过换 worker、开新任务或重启上下文重置总成本。
技术事实未知时先做一次有界调查；若仍不能判定，要诚实呈现未知。**真实目标不明、要求冲突、重大取舍、风险接受或超出授权时交用户拍板**，附事实、选项、推荐和影响。不要替用户猜，也不要把普通实现选择和可自行查明的问题一律上交。

## 5. 务实的质量与检查成本

保护真实项目资产和结果：不损坏存档/原件，不泄露凭据和隐藏游戏信息，不越权执行，不在 unknown 后重发；预算/Stop 应真实释放控制，历史失败不能改写。原生规则可信不等于任意插件/回调都可信。

每项额外防护要说得出：针对什么实际故障或可信风险、后果有多大、目前怎样验证、成本是否合算。可逆、低影响的内部改动用轻检查；外部代码执行、原始数据、控制权和公共语义用针对性反例。只因“理论上可能”而无限枚举极罕见风险，不是默认工作。必要时把剩余风险和代价交用户决定。

不依靠原生类别名单证明所有行为纯净，也不为跑通删除仍有意义的安全断言。以原生事件/状态决定就绪；时间用于调度/防卡死，不能制造成功。Reference 是首选对照实现，但其投影也可能出错；按原生事实定位分叉 owner。

验证顺序与复用由 [TESTING](TESTING.md) 唯一维护：编辑时最小忠实检查，稳定候选一次所选门；不在每次小改动后重跑整局/全套。不借旧绿色，不靠删断言/缩分母转绿。真实调用链检查要尽早做；小改动不需要新游戏/全库重审。

记录完整计划/尝试分母、胜/负、截断、基础设施中断、unknown和首卡点。不同核心/产物及修复后重跑分列。到死亡终局证明运行可用性，不证明策略强度、全机制覆盖或 Host 等价。

## 6. 谁决定，如何交付

负责人可在当前授权内决定内部实现、复用、任务拆分、有限调查和相关测试。用户决定真实目标/范围冲突、协议例外、研究配置/数据使用、新费用、PR merge/close及未获授权的部署/删除。已有明确授权不重复申请；批准某PR不批准另一个。

交付一屏结论：目的、精确产物/提交、可用行为、实际验证与副作用、未完成项、是否可合并/可运行、唯一下一步。长原件就地链接；不默认制作大ZIP、重复hash整库或重抄历史。需要离机转移/恢复时才制作相应包。

GitHub 使用 [WORKFLOW](DEVELOPMENT_WORKFLOW.md)：develop唯一集成线；一个结果一短分支/PR，允许有用未完成增量开草稿。依赖未合并工作必须写明基线；不要为文档任务提交整个未验收产品栈。源码版本与协议版本、实际安装版本分别维护，不能用分支名代替产物身份。

Auto-fix/外部作者只有一个明确写入owner。观察者只观察，不自行修复/重跑；自动修复也使用同一任务范围和停止条件，不能借CI无限续命。远端变化先看增量影响，不悄悄覆盖别人或不断重审全部历史。

## 7. 规范如何维护和保持

[PROJECT_SYSTEM](PROJECT_SYSTEM.md) 拥有文档归属：README讲项目，AGENTS给入口与硬边界，本文件管日常工作，AI_COLLABORATION补AI细则，任务卡管本轮，规格/ADR管合同和设计，TESTING管验证，WORKFLOW管Git发布，CURRENT管当前指路。不要把它们都写成同一份长手册。

改规则必须源于明确用户决定、真实失误或反复成本，说明它替代哪条旧规则；在原owner处改，搜索活动入口中的冲突，保留Git历史即可，不要求再造归档副本。规则是手段：不能被执行、收益不足或反复诱发偏航，就修正/删除它。

当前规范本轮就建立并验收，不等待P1结束。此后随真实问题维护；不安排自动周期全库审计或管理重构。是否再做整版审计由实际变化/使用反馈决定，不能把它设成未来产品工作的无限前置。

规范、测试设施和管理修订属于支持性维护，单独说明解决了什么实际摩擦；不能计作新增游戏能力、策略提升或训练进展。不因这一轮改过规则就持续安排规范建设。够用即可，后续真实问题出现时在原owner改。

有效性的三个观察：使用者是否得到可用增量；第一次真实链路反馈有多快；重复调查/检查/交接是否减少。提交数、文档字数、测试数、worker数和token消耗都不是价值指标。新成员接手失败是规范缺陷线索，优先修入口或矛盾，不让每位新人重读所有历史。


## 8. 测试与其他工程事项怎样进入同一个交付

测试是开发中的反馈工具：帮助确认改动满足需求、尽早发现错误、降低后续修改成本。需求和用户价值先于测试；测试也可能错，不能为了符合旧断言把正确产品改坏。[TESTING](TESTING.md#test-design-and-maintenance) 唯一维护新增、复用、维护、隔离和退役规则。任务卡写必要的检查与成本，PR给实际结果；不再另填测试管理表。真实链路、数据可信与策略质量分别验证，单元绿、跑到死亡和学习有效不能互相替代。

下表是按需路由，不是每个任务的全套前置检查。只处理本次受影响事项；已有负责人和机制够用就复用。

| 发生什么变化 | 原有owner与最小处理 |
|---|---|
| 需求/优先级/验收取舍 | 当前任务；长期公开语义决定归规格/ADR。先明确用户能力与非目标，变更验收需显式说明，不能追着实现改目标。 |
| 代码、架构、接口 | 组件guide、ARCHITECTURE/COMPONENTS；真实调用链和受影响消费者决定边界。有限重构可随修复做，不新建假想框架。 |
| 测试或反馈成本 | TESTING；保留必要信号，删除重复/失效覆盖，修改测试与行为同步。发现慢先测成本，不直接加机器或扩大测试层级。 |
| Git、CI、发布与回滚 | DEVELOPMENT_WORKFLOW；短PR、单写者、必要门、明确运行版本。集成不等于部署，只有改变可执行交付才考虑相应发布。 |
| 协议/数据/模型兼容 | VERSIONING及各合同；记录受影响版本、实际使用者和迁移/退役条件。不要求无关组件一起升级，不删历史原件。 |
| 依赖、构建、环境配置 | 现有锁文件/构建脚本/组件guide；固定可复现输入，检查实际受影响路径，凭据留环境。新增依赖要有现实收益，维护随真实升级需求进行。 |
| 运行故障、性能或恢复 | Host/Runtime/应用原owner；保存够定位的原错误与阶段，按影响止损/回滚，修最先错误的事实。不是每个故障都开安全或架构工程。 |
| 数据、训练与评测 | Evidence与研究owner；原件、投影、数据使用授权、固定评测条件和完整分母分开。未见评测与调试种子分开，现有研究冻结继续有效。 |
| 文档、交接和资产清理 | PROJECT_SYSTEM与CURRENT；更改影响到的入口/声明，短增量交接。只有不再需要且有权限的工作树/资产才清理，不以数量目标批量删除。 |

主管在已批准目标内可以自主派发下一项有界任务，无需每次让用户重新授权；但完成当前任务不自动获得另一个目标，历史待办也不能自行复活。重要未决取舍要交用户，普通可逆工程选择由负责人完成。
