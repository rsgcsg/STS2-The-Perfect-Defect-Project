# 工作规则：让下一圈更便宜，不丢东西

适用于人和 Agent。目标是可用、可验证、可维护的 STS2 Agent；用户当前指示、[AGENTS](../AGENTS.md) 和各合同的硬边界有效。本页管日常工作，细节按需查原指南。

## 1. 新事先回答五个问题

| 问题 | 写进现有任务 / issue / PR，小事几行即可 |
|---|---|
| 为什么做？ | 为谁解决什么，推动哪个分数或解除哪个阻碍；产物和验收是什么？ |
| 放在哪？ | 地图哪一格/连接，唯一负责人、准确基线、可写文件、不能碰的运行项。 |
| 以前有没有？ | 查[已有解法](RESOLVED_ISSUES.zh-CN.md)和相关原件：以前怎么解决，这次用不用、为什么。查够决策就停。 |
| 改哪一种？ | 表示/传输、实现替换、能力/语义、上层职责。满足原约定就局部改；表达不了需求才回合同或上层。 |
| 怎样交、哪里停？ | 输入来自谁、产物交谁、启动条件；权限、成本检查点、绝对截止和收尾余量。达标即交，到硬限留实物和剩余。 |

先核当前源码、未提交改动、在办任务和真实生产者/消费者。历史可被新证据推翻；不全史重审，也不只列文档名就称“查过”。任务或子项完成不能抹掉父能力的未完成项。

## 2. 概念够用即可

| 词 | 大白话、工作问题与区别 |
|---|---|
| 目标 / 分数板 | 要什么、实际做到什么；它让 Agent 更强，还是让下一圈更便宜？测试数不等于强度。 |
| 职责 / 链路 / 位置 | 谁负责什么、怎样连接；第一处错误归谁？按需要逐层拆，不是固定大图或操作步骤表。 |
| 节点 | 跑在哪个机器角色？采集/运行/训练/存储/控制可同机，不等于组件。 |
| 约定 / 协议 / 格式 | 两边要什么、给什么、失败意味着什么；协议实现交互，格式编码数据。相同 JSON 不证明含义相同。 |
| 实现 / 解耦 | 用什么完成职责；满足同一约定就能换一边。为什么另一边也得改？多种实现和重复业务状态机分别判断。 |
| 规则 / SOP / Skill | 规则说应怎样；SOP 在原指南写条件、入口、输入、结果、完成/失败/恢复；Skill 只补 Agent 非显然操作，不能成为第二 SOP。 |
| 收口 / 管理 / 收敛 | 收口保住本次结果；管理随改动维持；收敛是一次有界归位，不按训练轮次重复大工程。 |

每项业务一份含义、一处状态 owner；GUI/CLI/API/库映射它。Agent 不依赖点工作台，人用最方便的入口，复杂工作由后台完成。P1、模型输入、记录格式分别有约定；Host 差异、投影损失和模型输入差异分别归因。

## 3. Agent 怎样干活

- 主对话管目的、取舍、依赖、分工、集成和验收，也可亲自实现；关键原话、diff、结果亲核，判断不外包。
- 只委派能隔离、节省总成本的阅读/独立检查/细节。给问题、范围、停止点、交回物；只给必要上下文，返回短结论和证据位置。默认至多 3 个只读、1 个写入者，不嵌套；任务可更严，名额不必用满。
- 写入者独占分支/工作树/可变环境；共享合同和 CURRENT 各有唯一写入人。先解接口依赖再并行，重资源统一排期。同一修复/补证优先原执行者。
- 新独立任务用新对话；同一结果可续接。恢复核目标/禁止项、准确源码、已验结果、实际进程及 owner、唯一下一步和剩余时限，不能从旧标题复活任务。
- 授权内未验收且未到硬限就继续；派发/恢复/汇报不是完成。等待用真实闹钟或观察机制，约五分钟纯等待后做独立工作或一次有限诊断，不空轮询、不开范围外目标、不停正常服务。
- 卡按[第 8 节十三条工作规矩](#8-卡的十三条工作规矩)做。

## 4. 验证忠实，成本适当

先验最短真实生产者→传输/序列化→消费者及最低成本反例。稳定候选按 [TESTING](TESTING.md) / `check:plan` 选门：小文档/配置/不改约定的内部修复用相关检查和一次 CI；组件源码加非作者复核；合同、安装、真人数据、训练/评估加该声明所需真实链路、身份和 R2 收据。不能用档位跳掉必要检查，也不机械要求文档跑游戏。

用户 10-28 已批三条，具体做法见 [TESTING](TESTING.md#local-feedback-and-candidate-checks)：
1. 本地不重跑 CI 已跑的完整跨平台检查；本地只跑快检、相关小范围检查和原生/运行时/真游戏等 CI 跑不了的检查。合并前 CI 必须全绿。
2. CI 失败先读清原因再推，不在没读过的失败上叠新提交。
3. 冻结后不再加活；冻结后发现的新问题除非挡住本卡验收，一律写进报告“下一步”。

源码/测试、构建、安装/加载、真实运行、Human 来源、数据用途、模型效果分别报告。保留全部尝试、失败和 unknown；正常退出、死亡终局、CI 绿不替其它资格。测试也可能错，修首错层；不删有效断言、不缩分母、不碰运气重跑求绿。

明显问题：自动流程反复要人补命令、停用无提示、状态陈旧、坏派生挡新原件、同输入重复搬验、小改动长期无新事实、共享写入撞车。按阶段量时间、人工、Agent、开发、数据、GPU、存储、CPU，分实测和估算。连续两次不同原因失败或检查点无新事实，复查失败连接、要求和现成短路径；不自动加审计/重写。提速少搬少做、复用缓存/并发/批量，结果和身份须不变。

## 5. 缺陷、重构、资源

Managed 对齐结算后的公开逻辑事实，正常时钟只作诊断；实现按[Host M-1～M-8](../components/host-runtime/docs/MANAGED_P1_EQUIVALENCE.md#settled-logic-native-rules-and-replaceable-host-implementation)，字段取值与另版审批按[P1结算态原则](protocols/P1_GLOBAL_R1.zh-CN.md#41-录制原件派生p1的requires用户已批准)。

Managed 与 Reference 的差异按序判（用户 10-27 批）：规则/效果/随机数结果不同→修 Managed（M-1），同版本真游戏证据定对错；只是显示时机不同→先读两边独立逻辑字段，再用同快照结算规则另版，都不成立就登记交用户；卡住/记录不全→找它实际在等的原生操作并完成逻辑部分（M-6），修不了写清归属。界线不变：不把隐藏信息放进 P1、不改坐标/索引、不随意反射；不做第二套规则引擎；不靠放宽比较、改 unknown 判定或删分母求一致；不改写已有原件/Q/Store。

- 未修项进当前任务的原待办：位置、首次出现、挡什么、负责人/待派发卡。能复现且打断录制、训练数据或评估，立即形成修复卡并安排授权；发现者不在别的任务中顺手修。修后用原失败复查、补 RESOLVED_ISSUES；原 offer 的 unknown 不重投。
- 第二份业务实现、同坑反复、无关组件被牵连、上游大升级时评估重构。同 owner 且不改含义可随原任务；跨组件/身份/真人数据或含义变更先有界提案。按总成本排序，用同一忠实测试/重放比前后，不能见到两个同名函数就合并。
- 用户录制优先。游戏/安装先核进程和当前任务链接的共享登记，再登记占用、用完释放；用户可能在录时先问，一批用一个 Mod 组合。旧“空闲”不能覆盖用户新声明。
- 长任务按[容量 SOP](../python/docs/DATA_LIFECYCLE.md#workstation-capacity-before-long-tasks)核实际写入卷和累计峰值；评估/训练不抢重测试资源。低空间停在新局前，不自动删原件或放宽准入。

## 6. 权限：当前任务可收紧

| 档 | 当前卡范围内 |
|---|---|
| 自己做 | 调查、普通工程选择、必要实现/文档/检查、修自己 PR、同步 develop、开 PR；运行/安装守该卡窗口。 |
| 做完再报告 | 用户已给常设授权时，必跑门和 CI 通过、讨论解决、不改合同/删独有内容，可合本卡 PR 到 develop，按原授权保留 merge commit；组件源码尤其不可 squash/rebase。无该授权则逐 PR 批。 |
| 必须问 | 范围外新目标、main/正式发布、追加时间/费用、合同含义或重大上层取舍、付费训练、关他人 PR/删分支、独有内容/R2 删除。已批对象不重复问。 |

来源为用户 10-25 常设授权，只在当前卡内，替代无条件“每 PR 再问”的旧习惯。任务若要求 Draft 审批包，就停在 Draft，等批再合入/处置；“做完通常含 Ready”不能覆盖这一停止点。授权不随时间经过扩大。

## 7. 收口和维护

1. 报告前五行大白话：改了什么、能用什么、实际验证、未完/待决、下一步；原日志就地链接，末尾记耗时和主要成本。
2. 变化回原处：功能/操作→地图对应行和原 SOP，含义/理由→规格/DECISIONS/ADR，主线→唯一集成者替换 CURRENT；只改受影响处。重复问题补旧解法，未修项留原待办。
3. 任务目录 `CLOSEOUT.md` 记结束时间、结果/ref、活动进程及 owner、恢复/R2收据、保留/可重建项。CURRENT ≤40 行、无历史段由原 closeout 检查；语义新鲜度仍靠亲核。
4. 关闭/删除先归档 tag 并守原批准。收口满 7 天、无占用、非 tracked、有源码/锁可重建的依赖缓存可清并留收据；整目录先批，独有原件先 R2 完整读回。交接文件夹只移动不删，历史正文/失败不改写。
5. 以后才做的事记成 GitHub Issue 并加 `backlog` 标签，正文写触发条件、要做什么、背景；做完由 PR 写 `Fixes #N` 关闭。仓库公开，Issue 里不写个人用户名、本机路径或邮箱。

新建议先问目标、真实问题和已有解法；采纳就改原处一条、记理由，能并不另加。有用的未采纳取舍留原任务。入口失效、新人走错、重复成本或阶段变化才开限时管理任务；不让规则建设成为产品主线。稳定、反复且非显然的高成本流程才考虑 [Skill](PROJECT_SYSTEM.md#skills)。详细分工/恢复见 [AI_COLLABORATION](AI_COLLABORATION.md)，文件归属见 [PROJECT_SYSTEM](PROJECT_SYSTEM.md)，Git 见[开发流程](DEVELOPMENT_WORKFLOW.md)。

## 8. 卡的十三条工作规矩

用户 10-27 批第 1–6 条，10-28 批第 7–12 条，10-29 批第 13 条；这里是唯一原文。它们不放宽任何检查，只改检查的时机和做事方式。原因：完整检查反复跑、轮询占约三成步数、上下文太大、卡与卡互等。

1. **完整检查只在最后跑一次。** 开发中按 [TESTING](TESTING.md) 跑相关小范围检查；完整检查只对冻结候选跑，最好在单独 worktree 快照上，主工作树照常改文档和报告。失败先分清环境、测试还是代码；环境和测试问题记进报告“反复问题”，交给专门修复卡，不在本卡反复补。开跑前自检 Python 3.11、两处 npm、关键包、磁盘、工作树干净。
2. **等待用一次阻塞等完。** 等 CI、检查、批次用一次等到结束才返回的命令（如 `gh run watch`）并设闹钟；不每分钟 tail、sleep、看钟。
3. **上下文和报告短。** 报告前几行大白话，后面一张表，细节进证据文件、报告只写路径。上下文超过约 35 万 token 主动整理、开新上下文。
4. **合并排队。** 同一时间只有一张卡做“合并前最后验证”；要合并先看 develop 有没有正在验证的合并，有就等它合完。收尾只把最新 develop 普通合并进来一次、再验一次，途中不跟着别人每次合并重验。
5. **Managed 批次一张一张来。** 跑测速、量 unknown、评估等 Managed 批次前，在共享 GAME-SLOT 登记（`npm run slot -- configure --journal` 配置的那份）一行：哪张卡、几路、预计多久；别人的批次还在跑就先做不用 Managed 的部分。用户录制最优先。
6. **非作者复核按风险用。** 改 Host、P1、Connector、数据、安装、身份的找一个只读非作者复核；只改测试、文档、报告的不开复核子代理。
7. **全套核验只在关键节点。** 关键节点：装进日常；冻结训练集合、开始正式训练；模型成绩和评估入账；数据进 Store 或训练池；合并进 develop（CI 全绿 + 第 1 条完整检查）；删除；向用户报告“完成”。全套 = 身份和哈希、R2 冷读回、按第 6 条的非作者复核、回执文件。中间步骤（试跑、测速和诊断批次、草稿、临时产物、中间数据）只做轻量核验：关键输出一个哈希加一行说明写进工作目录日志，不写回执 JSON、不冷读回、不开复核。中间产物要成为关键节点输入时再补全套；拿不准就按关键节点做。
8. **收口清掉能重建的，Managed 本地副本读回后释放。** 卡收口时只在自己工作目录删 .venv、node_modules、包缓存、构建产物，以及已推送或合并、无未提交改动的临时源码副本和 worktree；一定保留 outputs、报告、STATE、日志、失败和 unknown 记录、回执、候选身份清单。还要接着做的卡环境可留到最终收口。Managed 每局证据传 R2 并读回核对后释放本地副本；unknown 和异常局保留到报告写完且 R2 读回通过；诊断档按 7 天规则；开跑前估算本地占用，剩余磁盘始终高于 15 GiB + 每路 2 GiB，不够就少开几路或分批，不降门槛。R2、别的卡目录、日常 Store、真人录制、日常安装、旧发行不碰。删除是关键节点：先列清单（路径、大小、为什么能重建或 R2 已有），删后报告释放多少、剩余多少。
9. **先跑完、收齐，再一次性修，最后一次性测。** 诊断、重放、测试、CI 遇到问题不停在第一个，能继续就跑完，所有问题按类别列一张表；一类一类修，中间只跑这一类的小检查；全部修完冻结候选，按第 1 条跑一次完整检查。只有出现 unknown、可能伤到真人录制或日常、要碰红线才立刻停。CI 失败也先读完全部失败、归类，一次改完再推。
10. **多做少问，卡住一件先做别的。** 卡的范围和红线以内自己判断，写一句理由；只有卡上列明的几类才停下问用户，其他拿不准的按更简单、能回头的做法先做，报告里列出。一件事等用户、等批次或等 CI 时先做不依赖它的部分，问题攒到收口一次问。中间步骤按第 7 条轻量核验，不每步写边界声明。
11. **写短。** GAME-SLOT 每条一行：`时间｜卡｜开始/结束/排队｜几路几局｜预计到几点｜一句备注`。报告前 3 行大白话，不出现内部编号和英文代码（放后面表里）。卡上“不做什么”只在报告最后写一次“都遵守了”，有例外才单写。每轮回复用户：做了什么、结果、要用户定什么，各一两句。
12. **运行节点同时最多 3 张卡干活。** 一张用 Managed 位，一张写代码或跑 CPU，一张训练或用 GPU；排队和等用户的不算，但排队时不跑重 CPU、不反复查别人状态，等通知或设一次闹钟。先后按总表维护人发的顺序，不在卡与卡之间自己协商。
13. **先找现成的。** 新开基础设施卡（启动器、调度、上报、检查点、数据格式、CI、看板、锁、存储、部署之类）先列现成工具或开源项目，再具体写为什么不用：接不上哪个节点、缺哪项项目硬要求（如公平玩家证据、身份哈希）、迁移要花多少。说不出就先用现成的。已经能用的不为换工具而迁移，除非收益明显大于迁移成本且用户批。新增治理检查器同样先过本条，并说清每次省多少时间。

**用户长期授权（10-28）**：学校 GPU——已批训练卡每次 5 小时内不用再问，但数据、代码、环境在分配前全部备好，用完立刻释放，不空等，本地能做的不占 GPU；超过 5 小时先问；登录和验证码由用户完成。真游戏窗口——每次都问用户，用户在玩时也照样问，同意后才开始。大卡——一个大目标一张卡，可自拆小步、开子任务或只读子代理，都归这张卡管，只写一份报告。
