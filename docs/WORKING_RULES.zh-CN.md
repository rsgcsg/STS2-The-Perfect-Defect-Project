# 推进与管理规则（2026-10-16 起，用户确认）

本文件是 Agent 日常推进的最高优先规则，和 `AGENTS.md` 的硬边界一起读。冲突时以用户最新指示为准。
历史文档里的流程描述如果比这里更重，按这里执行。

## 1. 目标：不混乱、能找到哪里错，而不是极致安全

这是个人游戏项目。质量的定义是：**真实能用、结果可复现、出错能定位**。
不是"证明每个环节都纯净"。

- 公平性红线不变：不泄露隐藏信息（抽牌顺序、未揭示奖励、随机结果、未来意图），不造原生操作，不在 unknown 投递后自动重发，不悄悄降级。
- 红线以外，**守卫只保留"真实检查"**：检查原生事实是否齐全、身份是否一致、动作是否在当前原生目录里。
  普通原生卡类/展示的固定名单若挡住游戏，应以实际原生 owner/调用语义取代；外来 callback、formatter 和被修改的有效方法仍须检查。正常游戏跑通不能证明任意回调只读，不能为转绿删除尚有效的安全断言。
- **以原生事件或原生状态为准，不靠读秒。** 是否稳定、是否就绪、能否继续，都由原生事件或状态判断。只有原生确实没有信号、或原来就是计时实现时才计时，并且要在文档里写明原因；超时只用来防卡死，要明确停下并记录。
- 原版游戏的原生逻辑默认可信；先跑通原版真实逻辑，Mod 支持以后再加，规则相同。
- 协议例外（为了粒度或可用性放弃某个原生细节）**必须先交用户审核，再写进协议文档的"登记例外"表**，不能在代码里悄悄拒绝或悄悄放行。

## 2. 真相源与等价

- STS2 原生规则和当前玩家合法可见事实是真相；Reference（真实游戏 + Mod）是首选对照实现，其 Connector 投影也可能有缺陷。Managed（无界面宿主）按同一合同对照。
- 两端等价的口径是：**把 Reference 的真实记录在 Managed 上重放对比**。出现分叉先定位到原生事实、Reference/Managed 投影或共享核心，不预设是哪端错；决策前缀和终局结果都要比较。
- Managed 的要求：在 P1 语境里绝大多数情况和原版一致，功能齐全、逻辑相同即可。不追求逐字节相同。

## 3. 推进方式

1. **先打通一条竖切，再铺宽。** 先用最短真实路径发现接线问题；修复时先做能重现该风险的廉价检查，再回到同一真实路径，最后扩覆盖。不要求每次修复都先跑一整局。
   只有单元测试通过的部件不叫"完成"。
2. **同时进行的主题 ≤ 3 个。** 新主题要等一个旧主题收口（合入或明确放弃）后才开。
3. **每个可验证的增量当天收口**：提交、写一句结果、合入或标记 WIP。不要堆 3 天不收口的分支。
4. **任务以可验证能力或真实失败为单位。** 一个任务 = 明确用户需要/可复现失败 + 原因 + 实现/修复 + 检测 + 实际结果。已有失败记录种子、宿主、命令、步数和原始报错；新能力或可被反例证伪的安全缺口不必等真实用户受损后才成为任务。
   不以笼统的"重构某层"或"补齐某规范"为任务；应指向明确用户能力、真实失败或具体可证伪风险。
5. **复现后修复，同口径复验。** 先重放原失败或跑最小相关场景，稳定候选才扩同一套件；不在每个小改动后跑40/20局。报告计划、尝试、终局胜/负、截断/基础设施中断、unknown及首卡点；不同core/产物或修复后单局重跑分列，不能拼成同候选通过率。
6. **停止线写在任务里。** 每个任务开始前写清"做到什么就停"。达到就收口交付，不顺手扩大。

## 4. Agent 协作与沟通

- **一个整合负责人**（当前：主工程 Agent）。它负责拆任务、审结果、提交、合入草稿 PR。子 Agent 只在自己的 worktree 改代码，不碰别人的。
- **交接只写增量**：这次改了什么、跑了什么命令、结果数字、下一个真实卡点、复现命令。≤ 1 屏。不重复贴历史背景。
- **新 Agent 启动只读 4 个文件**：`README.md` → `docs/memory/CURRENT.md`（≤ 1 屏）→ 本文件 → 当前任务涉及的 P1 权威文档（`docs/protocols/P1_GLOBAL_R1.zh-CN.md`）。其他文档按需查，不要求通读。
- **子 Agent 的输出不是证据**，直到负责人核对过代码、测试和运行原件。
- 子 Agent 不能写共享 `.git` 时，交付 `implementation.patch` + `commit-message.txt`，由负责人提交。
- 普通实现和可逆修复由负责人决定；需要用户拍板的事（实质产品范围、协议例外、新费用/研究配置、合并/发布/删除）集中列在一处，写清选项和推荐，不散在长报告里。

## 5. 省 token

- 大日志、证据、原始帧不贴进对话；只引用路径和摘要数字。
- 审计、文档整理、搜索、批量测试、单个明确 bug 的修复可以交给便宜/并行的子 Agent，负责人只审结论和 diff。
- 不重复计算：一个候选构建只算一次 BOM/身份；同一提交的测试结果不重跑，引用即可（TESTING.md 的复用规则）。
- CURRENT.md 只写"现在是什么、下一步是什么"，不写历史。历史在 git 和 `docs/evidence/`。

## 6. 标准入口（复现用）

- 套件：`node tools/p1-suite.mjs --host managed|reference ...`（用法见文件头）。输出 `report.json`，带完整分母和卡点原因。
- 单局回放检查：`sts2-p1 replay --run-directory <dir>`。
- Reference→Managed 对照：`sts2-p1 trajectory --run-directory <ref-run> --out t.json`，然后用 `examples/p1/replay_agent.mjs t.json report.jsonl` 作为 Managed 上的 Agent 跑同一种子。

## 7. GitHub、分支与版本

- `develop` 是唯一集成线；`main` 只在发布时更新。不直推，不 force-push。
- 一个主题一个短分支（`<agent>/<topic>`），从最新 `origin/develop` 切出，最多存活几天。合入用普通 merge（保留组件 source revision）。
- 合入、关闭 PR、删除分支或 worktree、部署、发布，都要用户逐项批准。
- **基线收敛点**：一条竖切在真实宿主上跑通并有套件报告时，就开草稿 PR 收敛到 develop，不等"全部完成"。
- worktree 用完（已合入或已放弃、无未提交改动、无 `.local` 数据）就申请清理。可重建构建产物只在确认无活动消费者、非安装/证据原件、且所属任务允许后清理；不能批量按目录名删除其他活跃任务的依赖。
- 版本：协议用 profile + revision（如 `p1-global-r1` r1.1）。改语义就升 revision，并在协议文档的变更表写一行。

## 8. 文档

- 每个主题一份权威文档；其他文档在开头写一行"背景/历史，权威见 X"，不再并行维护。
- 文档写"是什么、为什么、怎么验收、已知缺口、登记例外"，不写过程流水。
- 过时的计划和交接放 `docs/evidence/` 或归档，不留在活动入口里。
