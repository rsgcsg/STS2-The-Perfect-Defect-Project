日期：2026-10-06。版本：0.4。状态：**P0/P2 基础设计，已与 P5 的 D-M2 贯通实例和详细场景协调；不是 G1 接受或运行资格。**

完整交付入口现在是 [P0–P5 交付与验收](BASELINE_ACCEPTANCE_PLAN.zh-CN.md)，本文提供需求与上层结构。事实见 [P1](../evidence/BASELINE_P1_AUDIT_2026-10-06.md)，任务见 [唯一任务表](../plans/BASELINE_TASKS.zh-CN.md)。用户已授权 P5 的详细设计与有界验证，并指定封装 D-M2、时序 N、后续 Z/O 为优先实例；没有授权生产协议实现、真实数据用途修改、训练、安装、部署、合并、发布或旧分支删除。

## 1. 我们究竟要建立什么

目标是在不超出声明的原生玩家信息边界的条件下，建立能真实使用、不断学习和可靠比较的 STS2 Agent 系统。环境、记录、数据、训练、评估和分发必须连接成同一条可追溯的改进流程。基础设施的价值由它是否帮助这个目标判断，而不是由功能或文档数量判断。

“最强”是研究方向，不能成为没有条件的完成声明。一次比较必须明确任务、游戏与内容版本、起始条件、信息能力、Agent 组成、推理资源、接管规则和评价方法。工程基线通过不等于策略强；训练结束也不等于模型已经能在游戏中使用。

本轮先确定需求、事实和上层位置，再进入具体协议、例子、成本与测试的设计。抽牌堆的原生打开、虚拟查看、直接聚合只是局部设计选项，**没有选定任何一种为默认方案，也没有把它们当作三套完整协议**。

同一个奖励例子会被多次使用，但输出不同：P0 要求支持“看过再决定”的任务；P1 说明旧 M0 重访输入无区别、保护器与策略分离；P2 把事件提供、状态维护、轨迹记录、任务评价分别交给正确 owner；P3/P4 再决定事件和输入具体形式；P5 检查两个当前页面相同而历史不同的案例。不得把“都提到了记忆”误认为任务边界没有区别。

## 2. P2：上层系统分成三条责任线

| 责任线 | 负责什么 | 关键输出 |
| --- | --- | --- |
| 环境与交互事实 | 世界承载、公开交互、真实绑定、执行、生命周期、采集与来源验证 | 环境实例、交互反馈、不可变事实记录 |
| 任务与学习 | 模型和 Agent、数据语义、表示、训练目标、实验和评价 | 数据视图、模型/Agent 包、评估与研究结论 |
| 执行与产品 | 资源、作业、存储、索引、权限、传输、恢复、发行与用户入口 | 可执行用例、真实任务状态、分发和运行证据 |

这是逻辑责任划分，不是要求创建三个仓库、九个服务或新的巨型管理框架。现有单仓结构可以继续承接。具体目录移动只有在真实职责和消费者明确后才做。

整体流程是：

    世界与 Host → 交互环境 ↔ 参与者（Human / Agent）
                         ↓ 实际交互及来源
                       原始记录
                         ↓ 验证、转换与用途判定
                       数据视图
                         ↓ 表示、训练、实验与评价
                    模型或组合 Agent
                         ↓ 安装、绑定、实际运行
                       交互环境

执行与产品能力支撑各阶段，不另造游戏规则、研究标签或模型质量结论。用户可以只录制、只分析、只运行或只评估，不必每次走完整条链。

## 3. 统一术语与责任

| 对象 | 定义 | 边界 |
| --- | --- | --- |
| 世界 | 决定实际演化、规则、效果和随机性的过程 | 原生 STS2 是当前规则参考；独立模拟器须声明行为目标和验证范围 |
| Host | 承载世界并提供运行身份、生命周期和受支持管理能力的宿主 | 不决定研究奖励或策略 |
| 交互协议 | 参与者可获得的信息、操作、时序、反馈和生命周期的规范 | 规范本身不调用 Host |
| 协议实现/环境适配器 | 调用 Host 并维护必要交互状态，将能力实现为协议 | 不通过消费者重建原生合法性 |
| 环境实例 | 指定世界、Host、协议实现与起始条件的一次运行 | 相同 JSON 不证明相同行为 |
| 参与者 | 通过协议交互的人或 Agent | Human 与 Agent 的来源证明分别保留 |
| 任务 | 输入输出含义、目标、允许能力、预算、终止和评价的约定 | 不是模型代码或单次作业的同义词 |
| 模型 | 为声明任务提供表示、预测、生成、评分或控制能力的计算对象 | 可以组合、有状态或无状态，不必直接输出游戏动作 |
| Agent | 持续接收环境信息并产生请求以追求任务目标的系统 | 可以整体作为模型，或包含多个模型与固定组件 |
| 记录 | 实际捕获事件及其来源、顺序、已知关系和缺口 | 不自动是训练样本或优秀示范 |
| 数据视图 | 按明确转换、选择和用途从来源产生的派生产物 | 不改写原始证据或抹掉历史用途 |
| 实验 | 围绕问题固定条件、执行、比较并解释结果的过程 | 独立于执行地点和界面 |

对原生实现，STS2 保持规则、效果、RNG 和 Commit 权威；Connector 保持公开观察、完整目标操作及确切绑定/复验责任；Annotator/Evidence 保持采集与验证责任。更高层不因名称变化获得隐藏信息、原生操作数或第二套合法性权威。

## 4. 模型、状态和目标怎样连接

一次计算可以写成 y = f(x)，也可以写成 (y, z_next) = F(x, z)。把后者输入合并为 (x, z)，它仍是函数。区别在连续运行边界：谁保存 z_next 并供下一次计算使用。

因此，网络调用无状态、但外部每次提供历史时，整个 Agent 仍有历史能力。内部状态表示正常维护责任属于组件，不表示外部不能调试、保存或干预。干预必须产生明确的实验或运行条件。

必须分别描述固定参数、会话状态、外部历史、性能缓存和训练状态。训练目标、任务目标、评价指标和验收条件有关联但不相同。完整 Agent 必须接受整体任务评价；不强制所有子组件通过一个损失函数联合训练。

若两段历史形成相同有效输入和相同内部状态，固定决策组件就产生相同输出或输出分布。仅增加训练不能让它在部署时获得缺失的重访依据。它可能学会总是退出，但无法可靠实现要求区分首次查看与再次返回的条件策略。循环保护可以限制损失，不因此证明策略学会该能力。

## 5. 交互协议首先服务需求，具体方案留在 P3–P5

抽牌堆例子有三个局部选项：真实打开原生页；协议维护虚拟资料页；直接聚合公开内容。各自需要的 Host 能力、状态、时序、记录和模型输入都不同。地图、持有物、奖励查看、暂选确认等也要经过相同分析。

每项能力至少比较：真实任务需要、适用 Agent、实验可归因性、原生条件和副作用、信息提供时机、上下文长度、编码/推理/传输成本、操作数量、历史负担、记录可转换性、Host 可实现性及维护风险。

单项方案最优不等于组合后的协议最优。P3 要形成少量内部一致的完整候选；P5 用贯穿案例和必要测量判断。不得用局部示例提前冻结默认协议，不得为了省 token 静默删掉必需候选或隐瞒信息缺失。

公开观察 O 不是完整世界 X。通常无需完整知道 X，协议可以直接规定公开历史、允许请求及反馈。一次 O—操作—后续 O 不是自动成立的马尔可夫转换，也不自动是已证明因果后继。

Host 侧描述可捕获的公开事实、确切操作及生命周期能力；Agent 侧描述目标协议的观察、操作、反馈和历史。协议实现负责两者映射。聚合必须在有效交互位置上保持一致；不能混用旧手牌、新牌堆和失效操作。若 Host 的读取实际上要打开 UI，必须验证其副作用与目标协议一致，不能将它冒称为无副作用读取。

当前尚未决定：默认信息策略、动作粒度、协议内页面/查询状态、事件粒度、成本口径、历史提供方式、运行预算阈值和新 wire/schema。具体 JSON 和参数必须在后续决策中产生。

## 6. 原始记录怎样支持目标协议

记录是行车记录仪，不是人的知识状态。可记录公开事实捕获、真正提供的输入、行为见证、请求/执行反馈、后续观察和生命周期。Human 是否注意、理解或预测了某事，通常不可直接验证。

一份原生记录可以经明确转换形成一种或多种目标协议轨迹。转换必须证明目标观察有对应时点的依据、操作有正确映射、顺序成立、对象关系保持、被省略步骤有抽象规则，且未知和缺口未被补成成功。

例如，原生“打开牌堆—查看—关闭—出牌”可以在某个聚合协议下投影成“含牌堆的观察—出牌”。但目标要求的每个时点都必须有足够事实；第二回合读取的牌堆不能无依据地填回第一回合。

三种声明分开：

1. 轨迹符合：转换结果满足目标协议的观察、操作和顺序规则。
2. 实际重放：从匹配起点执行该轨迹，得到声明范围内的实际匹配结果。
3. 行为监督：标签确实来自该来源，但信息重表达不证明 Human 当时阅读了同一份模型输入。

随机性、起点和恢复能力影响重放；一条轨迹匹配不能证明两个 Host 对所有策略等价。允许忽略哪些 UI 步骤、ID、时间或成本必须预先规定，不能在发现差异后临时删字段。

## 7. 数据、历史与训练

    原始证据 → 验证与用途能力 → 目标协议轨迹/局部样本
             → 模型表示与合法历史前缀 → 训练或评价

M2 等状态模型依赖的顺序，来自协议的交互语义、记录的实际捕获、数据视图的资格判断和训练器的状态更新四层共同约定。原生点击历史不必等于目标协议历史。

预测当前选择前，不得把当前标签写入记忆。切窗口不等于换局，截断梯度不等于清空状态，缺少可靠历史不能冒充连续轨迹。观察-only 与操作/反馈历史是不同条件；没有一种被预设为本项目所有模型的强制形式。

旧数据按用途审计，不整体盖“可用”或“不可用”的章：可靠单步标签可能保留；执行相邻链未必证明观察历史完整；缺序记录不能直接训练所要求的连续历史；已使用 dev 不会因新 schema 变成全新 held-out。允许新完整历史基线没有任何合格旧来源。尚未完成全语料迁移审计，不能预报保留数量。

旧权重、编码器和外壳分别评估。新外壳可符合新接口，但不能自动让权重理解新信息；兼容失败时可以重训或退役。原始资料和历史结论保持原义，不以永久兼容所有旧实现为前提。

## 8. 学习、评估与工程服务的完整连接

### 第二条链已展开到哪里

P2 不再只把模型当作环境后面一个评分模块。完整第二条链是：任务→Agent 组成与状态→模型/横轴→数据与目标→训练与恢复→实验和评价→产物选择→实际接入→失败回流。责任层在本文件确定，具体合同在 P4。

| 工作面 | 第一版设计需要什么 | P3/P4 的对应交付 |
| --- | --- | --- |
| 模型/Agent | 组合边界、任务输入输出、可选状态、选择/规划方法及依赖 | ModelArtifact、AgentSpec、StatePolicy；不强制所有模型是 scorer |
| 历史研究地图 | A/B/C/D 与 PF/PL/RF/S、M0/M1/M2、N/Z/O、R 分开 | 保留旧家族和横轴，区分设计、源码、训练和实测；不跑全部组合 |
| 当前 M2 | native-text、confirmed、light-action 核心与 Public M2 各有输入和证据 | 最新 Public M2 的 observation-only/N-only 不成为新历史的通用定义 |
| Z 后继目标 | 真实执行分支、字段/latent 目标、掩码和共享梯度 | 不为未执行候选造后继，不以 latent 相近保证随机分布可辨 |
| O 结果目标 | 胜利、失败层数/进度、战斗末 HP、主动出牌与其他交互成本 | 逐项 horizon/mask/censor；预测、偏好、奖励、评价分开，不任意加权成奖励 |
| 训练/实验 | 输入序列、use/split、图/损失/优化配置、checkpoint、比较问题 | 新数据/目标不是旧 run 透明恢复；独立 Reset 与推理干预分开 |
| 评价 | 子模型、完整 Agent、运行监督与系统成本各自评估 | 按实际局/共同来源 group 解释结果，不把旧 dev 或重复终点当独立证据 |

历史 O 已有四项结果和终点表示的详细设计，不能在新系统里缩成 win 一个标签。P4 保留并补充单位、适用性与反例：低血可有策略价值，少动作可能来自早死，当前层不是失败层，未知不能填 0。[本轮学习史审计](../evidence/BASELINE_LEARNING_AUDIT_2026-10-06.md)提供精确来源。

第三条链同样有进入实现前的设计责任：P4 已列共同用例、TaskRequest/ResourceOffer/Placement、attempt 与产物验收状态、checkpoint 恢复、权限/用途/离线、分发组合和 CLI/API/GUI 关系。这不意味着学习 owner 包办工程；各 owning 角色共同评审。通用集群优化、任意插件与 GUI 像素不作为第一版设计前置。

### 第三条：应用服务、本地、云端与团队

核心能力首先是领域库和应用用例，再由 CLI、程序 API、GUI 调用。GUI 可以组合多个步骤，但不能重新解释训练结果、状态或权限。每个新模型不应另造上传、恢复、模型管理和游戏控制系统。

本地与云端是执行位置；团队是资源与访问关系。推荐连接为：封存记录→按授权验证/传输→固定数据与任务→选择合格资源→保存 attempt→执行→checkpoint/候选结果→owner 验收→模型/Agent 分发→本地运行与报告回流。

存储负责字节和不可变血缘，索引负责发现，操作数据库负责在途任务，数据 owner 负责用途，领域 owner 负责结果验收。共享界面可以汇总状态，但不建立第二份事实来源。

恢复至少区分传输、计算监督、训练、Agent 会话、世界和 Hub。未知提交不自动重发；停止请求不等于远端停止；种子新局不等于半局恢复；回滚代码不能抹掉较新的权限、用途或在途任务记录。下载过的字节不能被宣称已远程撤回，离线使用必须保留其实际授权与未知边界。

当前 cloud/Hub 能力及接缝见 P1；这里定义目标责任，不宣称通用资源调度、完整派生撤销或云端游戏 Host 已部署。

## 9. 组件连接和可复用位置

| 连接 | 需要约定的含义 | 现有承接位置，仅作复用起点 |
| --- | --- | --- |
| 世界/Host→环境 | 公开事实、原生绑定、生命周期、观察有效性 | Native Foundation、Host Runtime、Connector |
| 环境↔Agent | 目标协议、输入可用时刻、完整选项、请求和反馈 | Connector、Policy Runtime、模型 adapter |
| 交互→记录 | 事件来源、身份、顺序、已知关系、缺口 | Annotator、Agent Evidence、Evidence |
| 记录→数据 | 转换前提、用途能力、血缘、分组与曝光 | STPD data/fullrun、现有用途管理 |
| 数据↔模型 | 表示、标签、序列、掩码、可选状态规则 | representation、模型与训练实现 |
| 实验↔执行 | 任务身份、资源要求、attempt、恢复、结果验收 | 应用服务、Hub、compute/provider |
| 产物→运行 | 模型/Agent、依赖与契约、安装加载、回退 | ArtifactStore、发行与本地模型服务 |
| 所有能力→入口 | 同一用例、真实状态、可恢复错误 | CLI/API、Workbench、游戏内入口 |

同一原生事实仍由一个 owner 负责。上层提案不要求立即重排所有目录，也不创建一个同时拥有游戏规则、训练和所有作业的万能服务。

## 10. 用具体例子检验上层设计

| 例子 | 必须成立的关系 | 反例/可能否定设计的结果 | 后续 owner |
| --- | --- | --- | --- |
| 两张同名牌 | 对象不同，动作仍能精确执行 | 按牌名合并对象 | P3/E1 |
| 抽牌堆三种提供方式 | 每个候选都有明确时序、成本和记录规则 | 把三种混成不明的 query 开关 | P3/P5 |
| 原生查牌转目标轨迹 | 省略步骤但保留目标要求的同时点事实 | 拿后来的牌堆回填早先观察 | P4/E2 |
| 奖励首次与重访 | 所需历史进入完整 Agent 的有效状态/输入 | 同输入同状态却要求不同条件行为 | P3/P4/E3 |
| 打牌触发子选择 | 子交互可被处理，父过程随后继续 | 等父过程终结造成死锁 | P3/E1/E3 |
| Human 中途接管 | 来源、控制与历史边界保留 | 把接管动作算作 Agent 自主完成 | P4/E2 |
| 相同页面再次出现 | 事件发生与内容相等分开 | 内容去重删除真实重访 | P3/P4 |
| 训练窗口与恢复 | 状态、前缀、参数和事件位置符合契约 | 将 detach 当 reset 或随意载入旧状态 | P4/E3/E4 |
| 旧模型换外壳 | 新身份、输入和能力重新验证 | 张量形状相同就声称语义兼容 | P4/E3 |
| 云提交回复丢失 | 核对原 attempt，不重复提交 | 重新创建任务直到拿到回复 | E5 |
| 下载与用途撤销 | 按明确策略核对后续操作 | 声称删除了所有离线副本 | P4/E5 |
| 循环保护触发 | 监督机制与策略表现分别评价 | 安全停止被报告为任务成功 | P5/V1 |
| 同协议不同 Host | 接入与行为资格分开 | 相同 schema 等于原生等价 | P3/P5/V1 |
| 固定种子场景 | 标明新局、恢复或分叉能力 | 以 seed 重开冒充决策点恢复 | P3/E1 |

这些是 P2 的检验问题与预期边界，不是本轮执行过的场景测试。具体原生前提、阈值、数据与测试形状由 P3–P5 核实后确定。

## 13. 新工程师怎样审查本包，何时合入与建立基线

先读 P5 完整交付与场景册，再按本文件和 P1/学习审计核查需求、历史与责任，进入任务表的 G1 材料和后续包。应能在不询问聊天背景的情况下说明：输入、交付文件、依据、待决事项、反例、审查者和完成边界。若仍须猜测，交接尚未完成。

本轮先完成文档修订和独立复审，更新同一 Draft PR；本轮不合并。用户审阅并授权文档整合、最新 head 检查满足后，可将本包设计与工程规范合入 develop，不必等待 E 阶段。该合并只接受文档和工作方式，不通过 G1，也不推广运行版本。

之后 P3/P4/P5 的已审查设计增量可以经 PR 进入 develop，以明确 proposed/accepted 状态演进；G1 记录具体方案、范围和验收接受后，E0/E1–E6 再按依赖推进并持续合入。G2 先证明最小真实闭环；V1 完成声明范围；G3 才冻结工程基线。R1 从选定 develop 建临时 release，经实际资格与发布授权后晋级 main。
