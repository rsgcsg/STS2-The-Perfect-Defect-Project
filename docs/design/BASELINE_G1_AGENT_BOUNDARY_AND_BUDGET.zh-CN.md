# G1-RC2：交互边界、Agent/Model、数据转换与输入预算

日期：2026-10-08。状态：继续讨论的设计候选，G1未批准。**D01及其具体协议没有完全确定。** 本文修正RC1把“A方向已定”写得过强的问题；以下结构、推荐和样例均可调整，不是借解释细节冻结旧方案。本文优先于RC1冲突表述；[原总册](BASELINE_G1_REVIEW_PACKET.zh-CN.md)、[合同](BASELINE_G1_CONTRACTS.zh-CN.md)和[路线](BASELINE_G1_EXECUTION_ROADMAP.zh-CN.md)继续提供其余详细设计。

本轮做源码/原生只读审查、合成输入计量和规范整理；未操作游戏/存档、解锁、录Human、训练模型、修改生产组件或迁移其名称。

## 1. 先解释D03和D04

**D03问的是“这一刻交互参与者拿到哪些信息、以什么形式拿到”。** 比如当前战斗有三张手牌、两个敌人、一个已经打开的提示，那么可以给这些对象及其公开文字、数值、关系。未打开的奖励组内容是否也自动给，是一个要单独决定的信息政策；不能因为Host内部能读就默认公开。

**D04问的是“此刻可以提出哪些操作、如何对应到实际执行”。** 例如开始使用手牌c1、打开弃牌堆、结束回合；拿起c1后，操作可能变成移向敌人e1、移向e2、确认或取消。模型选了一个操作，环境还要检查原依据与当前原生条件。列表既可以完整拿出，也可以由完整集合提供查询；“所有动作合法可查”不等于“全部动作文字必须拼进一个模型prompt”。

例子里“c1/e1”是当前公开对象的局部引用，不是让Agent构造native对象或点击坐标。`ListActions/AllowedNext/Resolve`是协议资料操作，不会自己出牌；`Act(open_discard)`改变实际信息页；`Act(confirm_target)`才走对应原生输入；`Await`表示参与者愿意等，不是游戏里凭空增加一张等待牌。

这只是可解释的候选语义。是否保留原生每一层、合并某些操作、自动包含哪些资料、对外暴露什么时间，都仍需比较。合并若改变信息、成本或可取消机会，就是真实协议取舍；如果只改变内部调用次数且对外语义保持，则只是实现选择。

## 2. Agent和Model怎样命名才不混乱

采用用户提出的工作定义：**Agent是直接与声明协议交互、对外交付的完整实体；Model是其中一个具体计算结构。**

模型可以写成`y=f_theta(x)`；有状态调用写成`(y,w_next)=f_theta(x,w)`，状态作为显式输入输出仍是确定结构。采样时把随机源/状态作为声明的一部分。模型不等于LLM、不一定只有一个，也不天然懂HTTP、目录、控制租约或存档。

完整Agent可以含观察接收、历史整理、固定规则、模型、规划、信息策略、时机、选择和结果处理。它向外的输入输出、生命周期与资源要求作为AgentSpec交付；参数文件只是其中一个产物。**哪些通用工作包在Agent里、哪些由协议端SDK提供，不能仅靠Agent定义决定**，见下面的分配方案。

避免用“外壳”隐藏实际策略：若程序自动打开资料、选择等待时机、摘要历史或在坏输出时替选，它改变完整Agent行为，要有版本和评价。纯传输重试只读请求、缓存已封存目录、解析数据可以共用；也要保证不改变实际曝光/顺序。

STPD是当前研究实现位置，不是所有Agent或所有Model的总称。文档中的游戏Agent、工程协作者、Human操作者分别说明；“owner”写清是事实负责者、实现维护者还是运行授权者。

## 3. 协议三部分不是必须部署三层服务

```text
世界与Host实现
  ↕ H：Host能力合同（事实捕获、原生绑定、输入、结果、时钟）
P：协议语义与状态（公开投影、目录、有效期、事件/结果、失败含义）
  ↕ A：Agent交互合同（能收到什么、请求什么、何时有效）
封装Agent
  ↕ 模型计算接口／内部组件接口
Model(s)

管理／实验／产品系统 —— 实例准备、资源、作业、权限、产物与评价
```

H、P、A是逻辑合同，可在同一个进程/库中实现，也可跨进程。JSON/HTTP/IPC是绑定方式，不自动等于一种新协议。Agent的模型接口不是另一个游戏协议。管理API是否由封装Agent的某个角色持有，则由任务/权限范围决定，不能提前用目录名字定死。

### 三个可行的职责分配候选

这里的BND编号是**边界分配方案**，不是替代原19个任务ID，也不表示三套必然不同的游戏协议。

| 分配 | Agent内部 | 协议/SDK/服务侧 | 主要代价与适用处 |
| --- | --- | --- | --- |
| BND-1 较薄协议、较完整Agent客户端 | 自己维护接收游标、缓存、重连、请求账本、时机与模型状态 | 提供可靠原始公共事件、完整C和原生提交；最少便利服务 | 最灵活，但每个Agent容易重做竞态/恢复，难比较框架差异；适合特殊研究消费者，不建议人人手写 |
| BND-2 明确语义协议＋共享客户端库 | Agent持有策略、可学习/自选历史、W、规划、何时请求及选择 | 共用事件去重/重放、目录分页、Await机制、原请求查询、类型验证与控制机制；库可作为Agent依赖而非新服务 | 推荐进一步验证；减少重复，但必须避免SDK悄悄过滤事件/替选或变成策略引擎 |
| BND-3 有限任务Runner封装Agent | Agent交付包含episode driver，可能持有明确Prepare/Reset/Save/RunNext能力；内层policy只看gameplay口 | 平台按actor/用途/预算授权，区分游戏交互与任务管理；记录任务干预 | 适合自动评测/RL多局，减少外部拼装；授权范围和实验公平性更复杂，不应让游戏策略随意回档 |

BND-2与BND-3可组合：同一可复用参与者客户端，再由任务Runner组合管理功能。BND-1/2若对外曝光、时序和错误相同，可是同一协议的不同实现。若SDK只给稳定边界、自动打开未取得资料或丢中间事件，Agent面对的合同已经改变，须新profile/投影/对照，不能仍称仅“更方便”。

**当前建议并非最终决定：**以BND-2作为默认实验起点，把共同正确性机制集中复用；将BND-3作为有独立任务权限的组合方式。游戏策略本身通常不应通过任意底层入口管理存档，但完整实验Agent可以在获准任务中管理episode。最终需接受的是能力和行为范围，不是“所有叫Agent的对象永远不得调用管理API”。

### 按具体事情分配，不能只画几个方框

| 事情 | 原生/Host事实 | 协议核心/共享库 | 封装Agent/模型 | 管理或任务Runner |
| --- | --- | --- | --- | --- |
| 公开字段与完整可输入集合 | 原生决定；Host捕获与绑定 | 按已选公开政策投影，类型/版本/质量 | 可编码/检索，不能另造合法性 | 选择已资格profile，不临时偷偷加私有字段 |
| 事件去重/重连 | source事件与窗口真实 | 同ID重传、gap、只读恢复机制可共用 | 决定哪些事件进入哪个组件/W；不能伪连续 | 选择恢复/新segment的任务政策 |
| 记忆 | 不持有研究W | 可保存序列/游标，不替模型写策略记忆 | W、摘要、缓存和模型状态的语义 | checkpoint存储与生命周期协调 |
| 等待 | 原生ready/公共变化 | timer、predicate、race和控制中断机制 | 何时需要什么信息、选哪个Await | 任务deadline/停止权限 |
| 请求账本 | actual投递及可证明结果 | fingerprint、旧结果查询/冲突与unknown机制 | 接收结果，决定真正的新策略选择 | 不可核对时终止/换实例的权限 |
| 数据资格 | actual Human/native记录 | 保存事实/质量；不自动科研准入 | 学习者选择有声明的投影/目标 | 用途/数据/预算准入 |
| 开局/保存/重置/解锁 | 原生管理功能和实际副作用 | 管理合同与结果；不混成正常C | 仅持有明确任务许可的Runner可请求 | 默认此处准备实例并交参与者端使用 |
| 训练/算力/模型下载 | 与gameplay无关 | 不塞进玩法协议 | 实验Agent可以提出有界任务；Model只算数 | 作业/资源/use/产物服务执行 |

边界验收不是“有没有某层”，而是：相同消费者换Host是否只改H绑定；换Model是否不改游戏合法性；换客户端实现是否保留相同公开轨迹；断线后是否只有一个原请求owner；管理操作是否改变实验条件且被记录。

## 4. 一个直接交给Agent的具体例子

以下是候选对象，不是当前已部署schema，也不是整份送给模型的prompt：

```json
{
  "context": {"task": "play_current_run", "actor": "player", "profile": "proposal"},
  "basis": {"generation": "g4", "observation": "o21", "events_through": 73, "catalog": "C21"},
  "public": {
    "page": "combat", "energy": 3,
    "hand": [{"ref": "c1", "name": "示例牌", "cost": 1, "text": "当前原生公开正文"}],
    "enemies": [{"ref": "e1", "hp": 28, "intent": "当前公开意图"}],
    "focused": null, "visible_tips": []
  },
  "changes": [{"id": "e73", "kind": "public_facts_changed"}],
  "actions": {"catalog": "C21", "complete": true, "count": 3,
    "items": [{"ref": "a1", "verb": "begin_card", "card": "c1"},
              {"ref": "a2", "verb": "open_discard"}, {"ref": "a3", "verb": "end_turn"}]},
  "quality": {"declared_scope": "current_public_page", "missing_required": []}
}
```

这是**刻意缩小的示例目录**，不是现实战斗只应提供三项。真实目录必须含所选profile当前全部合法操作。管理凭据和底层对象不出现在public；角色/难度等真正公开的任务事实可以成为输入，私有测试seed及future targets不自动公开。

正常交互：Agent取到对象→共享库验版本/顺序→内部history/renderer/model处理→返回`Act(a1,basis)`→协议按原依据复验并报告delivery→实际公开target页出现→Agent再focus/confirm或cancel。父牌效果打开selector时，新的child页立即可决策，不能等父完成才给信息。

资料交互：Agent选`open_discard`→进入实际页→收到公开成员→决定返回或查看详情；页内`ListActions`只读当前目录，不能替它打开另一个原生页面。若改成一次`Inspect(discard)`直接返回信息，要定义Host如何实现、是否有UI副作用/时间成本、记录如何投影；它是待比较的抽象，不是名字相同就等价。

失败交互：旧a1遇到变化返回明确未投递stale→Agent取得新依据再选择。断线导致投递unknown→核原请求，不能再生成同动作碰碰运气。已知delivered而效果pending可以接受新事件、在原生允许时提出其他真正选择，不强制每张牌完全结算。

任务交互：普通参与者Agent在run结束后完成summary并报告；外部controller可准备下一局。BND-3实验Agent的Runner则可在其独立TaskPort调用`PrepareNextEpisode`，核管理回执、新generation和reset，再把新参与者Port交给内层policy。它不能在正常决策中以“重开一次更好赢”绕过任务结果。两种组合各自记录控制/终止、算力与干预条件，可比较但不混称同AgentSpec。

## 5. 第一个Model到底吃什么

当前**建议**先做“结构化协议对象→显式公开字段投影→一段展开状态文本；动作单独编码；W单独张量”的LightAction M2，作为最少复用的reference。不是把全原始JSON、完整C、所有历史和控制元数据一起塞进一个长prompt。结构化对象模型是重要对照候选，不因第一个reference而排除。

| 层 | 具体形式 | 作用/现状 |
| --- | --- | --- |
| Agent输入 | PublicFrame/事件、目录关系、任务与控制合同 | 主交互实体直接消费；确切wire和边界未冻结 |
| 状态renderer | 当前公开对象/资源/已揭示文字/关系→确定性展开文本 | 新建议；现有text_menu_inputs主要是compact JSON，不冒称已有此renderer |
| P_t | `int64[T]`状态token IDs | state tokenizer只在train拟合；不等于自然语言模型必用Qwen |
| W_(t-1) | `float[K,384]`，初始建议K1 | Model显式输入，输出W_t；不是历史文字或固定人工语义槽 |
| I_prev | 已确认且当时可用的先前实际输入，独立byte编码，或None | 不含当前预测标签；不把native unknown写成已成功 |
| F_t | 可用公开反馈的state tokens，或None | LightAction现有核心单独编码它；不是零成本拼到page |
| C_t | M个独立动作文本，每个UTF-8 byte序列加首尾标记 | 全评分reference完整读取；binding ID由Agent保管，不放进文本作特征 |
| Model计算 | `advance(P,W,I_prev,F)->W_t`；`score(W_t,C)->scores[M]` | 共享W写一次；每个候选只读它；logits不是胜率/奖励 |
| Agent输出 | 按声明选择规则选当前C成员，形成Act；或Timing选Await/Abstain | 同一Agent交付含模型、程序、数据合同和资源/恢复要求 |

具体可复用结构：ScratchTokenCore默认d=384、2层、6头、FF=1536、max_tokens=8192；页面经过core后投影到384，旧W/页面/先前实际输入/反馈经过固定槽注意力与gate更新。每个候选使用独立`Embedding(258,384)→Conv1d(k=3)→GELU→mean→Linear→LayerNorm`编码，再读W并经过transition/head得到分数。词表258是动作byte词表，不能与状态BPE词表混为一谈。

现有LightAction并非“永远一个Transformer调用”：page一次；非空feedback还会单独调用core。旧ExperimentalDSimple则把W、先前输入、反馈等嵌入进另一种core输入，W宽度跟core走，图不同；其旧在线adapter不是新LightAction完整Agent。首版可以选合并feedback为统一状态文本来满足“一次文本状态输入”，但那是**另一个输入/图调用配方**，需显式比较，不能声称现代码已这样做。

三种应比较的表示：①展开文本状态＋单独动作/W，复用成本最低；②typed对象模型，将cards/entities/numeric/relations分张量编码，减少重复文字但新增object masks、数值尺度、关系与未知处理；③联合状态＋动作长文本或prefix分支模型，支持预训练但需计完整上下文/分支成本。typed wire并不自动等于②，Model最终都接张量；选择要依据同信息条件的训用成本和闭环表现。

训练：实际来源→选择的假设/投影→Agent组件输入→顺序P/I/F/C和N masks→advance无标签事件、只在合格选择位置做完整C listwise CE→episode TBPTT→checkpoint/validator→整个Agent包。窗口detach不reset；同参数/输入/renderer训用一致。既有DSimple trainer机制可复用到LightAction新接缝；后者旧trainer仍每step有N且feedback=None。图/renderer/词表/时机/状态规则变化要新AgentSpec，不能仅换权重名称。

## 6. 有假设、有取舍的数据转换是允许的

目标不是只留下逐帧保真Human记录。为了某种训练任务，**可以丢掉某些信息、合并/重排表示、使用已声明假设、生成派生标签或近似样本**。关键是记录做了什么、失去了什么、适用于哪个任务，并检验结果是否有用；不要把派生样本冒充原始事实或给所有用途统一授证。

| 例子 | 可采用的研究转换 | 不应声称 |
| --- | --- | --- |
| 浏览过A/B又返回 | 对仅当前页M0舍弃浏览历史；对M2保留；或为信息更丰富目标把已取得资料聚合 | M0也学到了记忆；人原来就一次看到聚合内容 |
| 连续排队A/B | 假设推迟B不会改变目标任务相关结果，构造稳定边界D监督；记录使用execution S及恢复可提交状态的近似 | 人在S_B作决定、已有真实replay或严格等价 |
| 缺中间曝光 | 选择截断前缀训练；或用显式未知/插值/估计输入作探索性D数据，并独立标记 | 缺失已被真实补录、完整Human时机已证明 |
| 细动作太多 | 将open/focus/confirm映为粗动作标签，或删除纯导航 | 新协议具备同样取消/信息机会；可不验证粗动作如何实现 |
| 终局未知 | 做局部N，不要求Z/O；有明确统计假设可做删失建模 | 把未知随意填成输、把估计标签写成已知事实 |

每个ProjectionSpec增加`assumption_id, task/objective, retained_fields, dropped_fields, inferred_fields, mapping, validation_status, exclusions`。假设可处于proposed/tested/rejected，探索性训练可以使用proposed假设并明确报告；不能因为没有等价证明就一律禁止有价值的研究。与真实轨迹不同的样本另标D；若宣称目标协议真实可实现(T/R)或Human时机保真(H)，才需要对应更强证据。数据用途/来源权利仍保留，不通过转换洗掉Gold或原始来源。

## 7. 全角色A0–A10、教程和准备存档

设计目标扩为**当前基础游戏全部角色、A0–A10**，共享接口尽量角色无关。Defect A0保留为最早验收切片，而不是其他角色设计上不支持。不能仅凭差别不大就省略角色专有字段/机制：Regent星数与变化目标类型的Sovereign Blade，Necrobinder宠物/随从与生成Soul，Defect有序球及容量等均须进入公开事实/动作/记录矩阵。

精确已读原生构建中，升阶规则按`runLevel >= level`累积；A4影响药水槽，A10有双Boss。因此难度不只是一个数值标签。合理验收采用共享机制回归＋每角色基础旅程＋变更升阶点的targeted验证＋高阶连续任务；不是机械训练55个独立模型，也不是只验Defect一次就全勾选。详细采样量在执行计划固定；支持范围与实际资格按角色/阶层报告。

教程默认不是策略学习重点。推荐管理侧在隔离profile准备阶段关闭FTUE并检查结果；正常任务默认无教程。意外弹窗可以通过独立管理接口处理、暂停并重新准备，或由任务允许的通用关闭动作处理，必须记录其方式和控制来源；不能静默卡死/裁目录，也不把它变成默认模型必须学会的核心目标。显式教程测试profile可保留。

原生源码确认有`UnlockConsoleCmd`的`unlock all`，会保存进度并解锁内容/升阶到10；`unlock ascensions`附特定参数的分支并未完整实现。已有Host journey工具支持`--tutorials disable|enable`，但未查到通用Workbench unlock-all endpoint，不能写成已经可点的功能。

管理准备建议：隔离或明确选择profile→备份与当前身份→经原生管理入口解锁/关闭教程→核公开进度/角色/阶层→新开局→记录PrepareReceipt→交参与者接口。已有run保存开局时的unlock state，修改外部进度不改变已保存run；继续旧局、创建新局和迁移进度必须分别处理。此处没有执行任何存档操作；将来工具调用属于获授权任务准备，不属于Model自动出牌逻辑。

## 8. 复杂场景到底有多少动作

先区分三个不同量：原生内部/公开直接动作对数、协议当前菜单项数、模型实际评分候选数。因子化参数、逐次选择、原生页面或虚拟分类层会改变当前菜单项数与交互步数；即使外部菜单很短，底层完整关系仍有构建/复验成本。

| 场景/实现 | 即时动作计数表达 | 限制 |
| --- | --- | --- |
| 直接出牌/药水→目标 | `1 + Σ每牌合法目标数 + Σ每药水合法目标数` | 各项由原生决定，不能任意对象×动词；不含另加信息操作 |
| 原生持牌target页 | `1取消 + 2T(focus/confirm)`；untargeted通常至多2 | 当前mode不能同时再加root/商店/selector菜单 |
| 现有text-menu-v2 root | playable cards＋药水openers＋EndTurn＋可用资料入口＋information index | 分目标/确认/信息分类有额外协议步骤；不能只用root数字评价总成本 |
| 药水popup/target | popup至多3；target为T+1 | 不是同时把两页相加 |
| 逐次selector | N个可选/撤选＋当前confirm/cancel | 选择k张的未来组合数可能大，但即时C不等于组合数C(N,k) |
| 完整资料列表 | N条实际可inspect/hover能力＋返回等 | 取决于所选粒度与原生能力；当前holder可达缺口不能作新设计硬上限 |

正常原生手牌上限10、OrbCmd正常加槽路径最多10可核对。药水初始3，但某些方法允许增长；敌人、牌组/牌堆、遗物、状态容器路径没有建立统一全局最大值。**未找到上限不等于证明合法vanilla可以无限大；当前不能给可靠全游戏绝对最大token或动作数。** Connector已有512 presentation cap是实现限制，超限标truncated；它既不是游戏上限，也不能自动成为新协议限制。

为了预算，定义一个明确的压力包络：H10、敌人8、球10、占用药水5、遗物50、公开状态80、某资料页200张牌。它不是统计P99，也不证明该组合可在真实一局同时出现。

在这个包络下：全敌方单目标的直接战斗对数上界121；现有text-v2 root约22、held-target17、状态分类81。若选择在同一主逻辑页展平全部信息leaf，并假设每张牌有play/hover/inspect、每遗物有hover/inspect、每药水有popup/hover，则`3H+2R+2P+S+E+O+12=250`。这250是**另一粒度候选的假设目录**，不是现有root实测。200牌逐次selector约202；资料页单独inspect+back约201，若再加入每牌tooltip则会更多。10,000不是当前普通战斗的有据估计，但接口不应因没遇到就硬绑固定动作数。

## 10. 计算成本与超限处理

设状态T、反馈F、动作byte长度A_i、候选M、槽K、d384、core层L。LightAction状态core约`O(L(T²d+Td²))`，非空反馈另有同类F成本；W写入有固定槽attention及投影；候选CNN约`ΣO(3A_i d²)`，另有`O(MKd)`槽读取和`O(Md²)`head。非空I_prev也单独调用一次action encoder，另加`O(3A_prev d²)`及投影/归一化成本。**O(MK)只是其中一步，不是整模型成本。**

压力例子的候选CNN按5745个byte token、d384、kernel3粗算约25.4亿multiply-accumulate，仅为结构算术量，不是测得耗时；padding/batching/kernel/缓存/训练反传会改变实际开销。“轻量”相对于反复跑大状态encoder，不能当绝对便宜。可以评估批量候选编码、相同参数/动作文本下缓存、较窄编码器或结构化动作编码，但换图/信息或训练近似要新recipe。

因此建议先比较展开文本＋byte动作reference与对象/短结构动作方案，在固定完整C与公开信息下测状态/动作编码、W、score、传输/捕获各项。不要一开始把8192或512写成游戏最大。超限时：确定的无损去重/完整分页/模型支持的分块可以用；有损摘要或shortlist由AgentSpec声明并评估；环境不截C假装完整，模型不能静默截文字后继续声称同输入。模型资源不够可以明确Abstain或换获准兼容Agent，不能自动伪造分数补齐。
