## 2. 六大块的解释

1. 定方向：P0–P5/G1 查需求与事实，比较完整方案，用例子、反例与测试设计确认可实施范围。
2. 收基础：P1/E0 判断现有资产如何复用，不把“清空 PR”当工程目标。
3. 搭核心：E1–E3 让环境、记录和 Agent 采用共同含义。
4. 接工具：E4–E6 贯通学习、执行、云/本地、团队和可编程入口。
5. 证实基线：G2/V1/G3 先小闭环，再完整范围，不以各组件自测代替组合。
6. 交付研究：R1/R2 发布稳定组合，再有依据地扩大实验。

## 3. 依赖、并行与唯一 owner

    P0 + P1 → P2 → P3 ↔ P4 → P5 → G1
                 P5 的检查可及早反馈 P2/P3/P4
    G1 → E0 → E1 + E2 + E3
    稳定的产物/执行契约 → E4 + E5 → E6
    最小可用 E1–E6 → G2 → V1 → G3 → R1 / R2

上图是依赖，不要求所有调查和独立实现串行。数据盘点、原生机制、接口消费者和资源约束可并行查证。共享协议、事件顺序、恢复状态机、BOM 和集成 ref 各由一个 writer 负责；其他人不能为使自己的测试通过而改变共同含义。

各 owner 先引用同一契约版本和样例。基线或接口变化时，列出受影响消费者/任务，更新验收与版本，再继续依赖工作。没有真正独立的任务时不为占满槽位而派发。

已审查增量持续进入 develop，不等待 G3 才集中合并。main 只接选定正式批次。未知外部执行先核对原 attempt，不通过新任务或删除 journal 规避。

- **必须检验：**选项的上下文/动作/延迟成本；raw/target trace 的对应；状态重复更新；未知不重发；停止保护与策略结果分别判定；真实入口而非只测 fake；所有“不支持”是否仍留在覆盖矩阵。
- **边界/完成：**本轮 probe 限 synthetic JSON/reference 状态，无外部服务；原生仅解析代码。可选 6 项 Torch 预检因环境缺依赖而 0 执行，已列 E3 前置。神经/实机/云性能未测，不自动启动游戏、Human、GPU 或训练。G1 现在可据所列证据和未知作接受、拒绝或要求有界补充；不能把未测项填成 PASS。

## 7. 合并与基线建立的时点

| 时点 | 可整合内容 | 前提与非声明 |
| --- | --- | --- |
| 本轮文档修订后 | 同一 Draft PR 的 P0–P5、场景册、D-M2 参考链、有界探针及已有规范 | 独立复审、最新 head 检查、用户审阅；本轮没有 merge 授权 |
| 用户授权文档整合时 | 文档/规范进入 develop | 不等待 G1 才保存成果；不因此宣布协议已接受或推进 E 任务 |
| P3/P4/P5 设计过程中 | 已审查的版本化设计增量 | 明确 proposed/accepted，保留未决项；有界原型独立标识 |
| G1 后的 E0/E1–E6 | 通过相应验收的源码增量 | 按依赖持续 PR 到 develop；不等所有模块完成才首次联调 |
| G2 / V1 / G3 | 从真实小链扩展至声明范围，固定基线 | 使用上面的 gate 材料，不把合并数或 CI 当基线完成 |
| G3 后 R1 | 精确 release 候选、main 与原样发布产物 | full source/test 和所声称实际资格、回退、发布授权均满足 |

P5 已给基于入口/缺口的相对工作量和关键路径；日历排期要在 G1 决定范围/资源、实施包确认负责人和未测项后给出，不编固定日期。旧 PR 只有在唯一增量、运行/证据引用和替代关系核清后收口；main/develop 是长期主线，不以删到两个分支作为能力验收。
