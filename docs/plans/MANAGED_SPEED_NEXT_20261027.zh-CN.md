# Managed 下一版提速方案（M1，2026-10-27）

建议先复用本地 Store 暂存，减少每局对 R2 的小对象往返；再做有界并行读回和执行/保存流水线。先不重写传输、不复用游戏进程、不增加并发。正式成绩仍要完整 R2 typed 读回后才成立。

## 本轮核实后更改 Claude 建议的理由

- 每局证据已经是 tar.gz 包，不是约3,200个文件逐个上传；不再开一项“从零打包”工作。真正的小对象热点是 Runtime：127 payload，实测一局发布255 PUT、508 GET，52.84秒。
- 先测现成 `store=/ABS/private-store, peer=冻结R2`，不先新造批内Runtime缓存。单局已存在payload的保存A/B：相同已封存原件、相同publisher和父对象，保存116.66→28.96秒，artifact/content/archive/transfer身份完全相同，完整R2 typed均通过。
- 本地暂存不是无代价：首次完整训练祖先DAG只读复制250.72秒、566 GET、2.21GB本地占用，应由节点复用工作集，且收据显式计冷启动；8局/4路短批冷启动未必获益，不能只把87.70秒乘每局。
- 本次自然局实际P1决策数低于卡中“每局约1,000”；旧346d/s是不同raw引擎定义，不能直接承诺每局几秒。当前raw engine-lab在warmup遇“native card reward option no longer selectable”，0个有效计时决策；失败保留，不能拿无效平均CPU/速度作新上限。
- 大结构按卡先出方案，未在本轮做。早停只限制浪费，M051真实原生异步等待根因继续归M2，不宣称已修游戏机制。

带profiler/观察器的组仅用于归因，排除在主吞吐比较表外。

## 运行与保存的共同契约

应用的同一 durable ledger 是唯一槽位/分母权威。Runtime 管执行、Stop和原件；Host管准确世界身份与关闭；ArtifactStore/Evidence管完整性和读回。模型、输入、P1、Reference不因提速改变。输入为冻结种子、进度、原438、完整包pin和producer；输出为每槽原件、关闭收据、Store/R2读回和原结果。关闭失败、保存失败与unknown分别保留；不重offer unknown，不从“进程已关”推游戏结局。

本卡代码只加细分计时、manager诊断和120秒同原生snapshot settling早停；没有改保存语义/证据内容、推理算法或模型输入。实际产品版本Host46/Runtime52，旧安装保持原组合。下一轮开始前正常merge最新develop，确认T1/M2/M3共享文件owner。

## 下一版建议的有界交付

建议下一张M1只做1+2+3：复用现成暂存、每次读回有界并行、同账本有限保存队列，逐步打通最短正常入口，不新建调度服务。节点准备和批执行分开计时，每局原件/关闭/保存事实保持单一owner。建议目标是本机4路、完整正式证据、在录制资源头寸内，warm批墙钟比本轮同类基线至少降低30%；目标是下一轮门槛建议，尚不是本轮实绩，也不偷改unknown或自然局分母。先用预留的新种子，正常对照绑定同版本/同输入；unknown不重试。

如果用户选择更小范围，先1+2；如果追求RL采样成本，M2先明确正式/诊断/轨迹consumer，再合3，不把“每小时完成多少槽”当“每小时可训练多少合格轨迹”。进程复用、文本缓存、6/8路分别延期，避免同时换太多因素而说不清收益与结果。

M2接口保留：phase_seconds互斥大段；detail_seconds嵌套细分；每槽seed/producer/Host/Runtime/model/input/progress pin；exact Stop/close、unknown原因；完整preservation artifact/content ID；private registration/expected生命周期；保存前pending、最后readback通过才score。M1未引入档位、新奖励、新轨迹协议或unknown训练规则。


## 流水线的具体连接与停止条件（提案，尚未实现）

仍由同一应用账本管理一次offer：`reserved → executing → Runtime封存 → Host关闭已确认 → 等保存 → typed/R2读回已确认 → 最终结果`。执行工人保留下游需要的run目录、registration、expected及精确包pin，关闭Host后才把不可变保存任务交给有上限的保存池。保存池只搬验原件，不执行游戏。所谓“等保存”是下一版需设计的账本状态，**本轮没有新增这个字段或队列，M2当前只能消费既有结果/计时接口**。

建议初值4个执行工人、1–2个保存工人、最多4个等待保存的原件；先按本轮最大原件和并行解包峰值预留空间，继续守至少15GiB余量，达队列或空间限额就停止新offer并排空已开局。不要以同一块空闲磁盘同时承诺给执行与保存。若用户开始录制，则暂停新准入、通过原Stop/关闭结束已经必须退出的本卡工作；不强杀用户服务，不删除证据来腾位。

成功必须满足准确producer/模型/Host/Runtime/progress身份、每槽不重offer、Host实际关闭和完整本次R2 typed读回。保存失败保留源文件与同一任务身份，结果不能提前出分；只可恢复原保存操作，不重新打局。关闭未确认维持现有阻止新准入的规则；保存失败或未知不抹分母。整批完成时间包含最后保存尾巴。异常/重启/断网、两个保存工人首次共同发布同Runtime、磁盘背压、一个unknown而邻局正常继续都要用正常入口复查。

回滚只选择上一已验执行组合/调度方式；原件、旧ID、旧unknown和已冻结输入不回写。先验单局执行→关闭→保存，再验带一次保存失败的2局，最后同一固定新种子的1/4路正常对照；不能在多个版本/种子/推理方式同时改变时声称单项收益。

## 每小时收益的统一估算口径

为便于比较，下表只用同一个**示例工作负载**：每槽220秒、4个执行者、热工作集、没有新unknown和其它资源饱和，基准65.5槽/小时。它不是本轮实测吞吐，也不把几个不同种子/版本组拼成因果对照；公式是 `4×3600/(220−单项节省秒)`，冷启动和保存尾巴另扣。只有同一行可比较，其它行不能相加。
