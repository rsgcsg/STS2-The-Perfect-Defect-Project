## 1. 项目定位与范围

项目以 AI 研究和真实实战为主。1a 交付可重复的小规模实验与全场景运行工具，
不是先开发通用商业 SaaS。当前只服务一个团队、一个配置好的 Hub，沿用邀请白名单
和已有 member/admin 身份；不增加公开注册、多租户、团队创建、订阅计费或细粒度角色平台。

游戏内是默认且完整的工作台；同机浏览器和云网页是同一项目的其他入口。
完整指核心工作能执行、看状态、拿结果并恢复，不要求所有高级图表或商业化包装先完成。
功能按需进入相应页面；不能每进入采集、数据、训练或模型页又申请一次独立授权。

## 2. 一套产品授权，一次配置入口

用户在一张清晰的配置说明页点击“配置本机”即接受该页版本化的默认使用范围。
不再配置一次、绑定一次、采集签一次、每个模型或页面再授权一次。后台可组合多个已有
owner 操作，但前台只有一个设置任务，显示真实阶段并支持从未完成步骤继续。
不能把安装成功、成员登录成功、设备登记成功和原生就绪合成一个虚假成功状态。

默认说明页应说明以下事实，不使用隐藏或预勾选的额外授权：

> 为本机安装和管理 SpireAgent 的可信兼容组件，使用指定的项目数据目录，按需运行
> 数据处理、训练与模型功能。连接本团队后，按这里展示的默认采集用途和团队共享范围，
> 处理配置后主动开始录制的新数据，并共享范围内的模型与报告。可在设置页暂停同步或
> 停用本机授权。配置不会自行开始录制、训练或 AI 接管，也不会把历史私有文件自动上传。

实际文案必须展示真实下载源、安装/数据位置、团队名称、Hub 地址、数据类别、用途、
共享对象、自动上传规则和软件更新方式。若默认包含新 Agent 报告共享，必须同时明说，
且 Agent 报告不进入 Human 数据。旧单次分享实现不能被文档直接改成自动分享。
资源较大的可选包可以稍后在使用该功能时准备；显示大小/资源需求不是再建一套授权。
不以“配置本机”解释成无限扫描磁盘、任意命令执行、任意第三方数据分享或无限云消费。

### 设置流程

1. 检查本机已有配置、安装身份、正在运行的任务和同一 profile；复用而非重复登记设备。
2. 显示上述统一说明；用户点击“配置本机”后保存本地接受的范围/版本。
3. 准备已授权的兼容组件。未登录或断网可以先完成独立本地功能，不伪造团队授权。
4. 团队入口仅需要首次或必要时验证白名单账号。优先复用现有系统浏览器会话与设备
   连接流，完成后回到原设置任务；不复制第三方 cookie 或让用户粘贴 token。
5. 账号、Hub 和说明版本与用户接受的上下文一致后，由已有 owner 完成设备/采集范围
   登记与准备。若身份或共享范围变了，在同一设置页处理，不悄悄继承另一个人的许可。
6. 后续进入各功能页直接操作。点击“开始训练”“加载并接管”“同步此数据”是具体执行
   意图，不再弹出一套重复的通用授权表单。开始执行仍需当前资源、兼容性和数据用途检查。

登录验证回答“是不是这个白名单成员”；统一使用授权回答“这台电脑被允许做什么”。
二者共享一次 onboarding 体验，但配置按钮不能给非成员制造 Hub 访问权限。
换窗口不产生新成员或新同意记录；换设备仍要建立自己的设备身份。首次认证、凭据失效、
账号切换、撤销或用途实质扩大可以需要交互；不能承诺跨任意设备永远无需再次登录。

### 后台不合并成一个万能密钥

沿用 Hub Membership/Identity、LocalIdentity、CollectionFlow 和用途账的事实 owner。
“统一授权”不是新增第二个会员数据库、复制 Hub 数据库到本地绕过准入、让所有成员共用
一个 token，或把设备上传凭据当管理员凭据。底层会话可以各自刷新/轮换，前台不重复问。
需要新协议时走版本化合同和消费者回归；旧同意、软件版本、原始队列及失败回执原样保留。
当前源码的会话过期规则不能被“保持登录”的目标文案当成已有自动刷新能力。

本地自有数据可在本地权限范围内管理；项目数据的 Gold/用途/访问限制不会因退出登录消失。
一个成员视图不等于可读所有封存材料。保留已有最小 member/admin 区别，不扩大权限体系。

### 授权、执行与高风险变更

| 情况 | 产品行为 |
|---|---|
| 浏览页面、查看已授权数据、切换窗口 | 复用当前身份，不重复授权 |
| 明确点击开始录制/训练/接管 | 在默认范围内执行该操作，不因配置完成就自动启动 |
| 新采集数据的团队同步 | 在已展示并接受的默认范围内自动处理；本地模式未连接团队则不上传 |
| 历史本地资料、外来资料、用途/共享范围扩大 | 需要明确选择/变更范围；不得追溯伪造旧同意 |
| 日常兼容组件更新 | 可以在已接受的更新范围内自动准备，在安全边界启用，不打断在途运行 |
| 云预算、管理员发布、删除原件或生产恢复 | 已有权限/预算约束继续生效；没有授予的新风险不能被默认许可覆盖 |

云计算可采用管理员一次设定的真实总预算/任务限制，在范围内操作不重复索取通用授权。
现有零预算不自动变成非零，也不把执行 timeout 当费用上限；本次没有批准任何新云消费。

设置页集中展示账号、设备、统一范围、同步偏好和版本；提供暂停同步、退出团队会话、
停用本机的清晰区别。退出云登录不删除自有数据或中断自有本地训练；停用本机请求安全
停止相关后台活动和模型控制，明确在途/未确认状态。撤销阻止后续访问，不能撤回外部
已下载副本；离线设备不能谎称已收到云端撤销。不能静默改变历史退出/上传语义。

## 3. 本地、云、GitHub 和 Workshop 的关系

| 部分 | 它是什么 | 不是什么 |
|---|---|---|
| 游戏内工作台 | 完整产品入口、模型控制和各任务的可达界面 | 模型/训练引擎、第二个权限数据库 |
| 本机 SpireAgent 服务 | 安装和任务管理、本地文件、模型推理/训练、受控 Hub 客户端 | 必须依赖游戏存活的进程或云端任意控制代理 |
| 团队 Hub | 现有白名单成员、共享数据、用途账、模型/报告目录和受预算约束的云任务 | 每人安装一份的服务、多租户 SaaS 或游戏实时推理中转 |
| GitHub 仓库 | 源码、合同、PR、CI、任务和经过审查的发布依据 | 用户游戏数据仓库、在线会员库或生产状态本身 |
| GitHub Release/既有发布存储 | 固定安装包、校验和与发布组合的分发渠道 | 下载后即获得数据权限或安装/运行资格的证明 |
| Steam Workshop | 游戏 Mod 的发现、订阅和分发/更新渠道 | Hub 管理员、模型训练服务或完整环境已经就绪的证明 |

GitHub 的开发账号、团队工作台账号和 Steam 订阅不互相替代。普通用户无需提供 GitHub
写权限或云厂商凭据才能使用工作台。公开仓库只保留安全的源码/回执摘要，真实数据、
原始日志、权重、token 和本机私有路径按原有规则留在授权存储，不提交到源代码仓库。

本地自有数据路径：录制原件→本地核验/索引→固定数据/用途→训练→模型→本机实战。
团队路径：授权同步→Hub 核验和用途检查→共享不可变产物→有权下载/训练→新模型与报告。
相同内容用不可变身份关联，不代表所有字节都必须上传；所有同步展示范围和真实阶段。
云网页可在本机关闭后查看云资料，不能伪造本机在线。云浏览器不得凭一个登录态向任意
localhost 发送游戏命令。本机已授权任务不因面板关闭而取消；游戏绑定的控制随该实例退出。

## 4. 分发与更新统一成“团队推荐组合”

用户目标：Workshop 订阅并启用 Mod→游戏内“配置本机”→一次范围确认/必要登录→自检完成。
缺组件由受控配置器选择本平台的固定安装包，不要求用户先装 uv/npm/Python 或修改 PATH。
安装器使用独立用户目录，不污染用户开发环境；允许必要的系统安全确认，不绕过系统保护。
若无法直接自动启动下载程序，提供一个可信安装包和自动返回/重连的短流程，不以永久
手工安装说明代替完成。离线团队包复用同一版本组合/配置器，不是第二套产品。

复用 `platform-bom.json`、`python/configs/developer/combination-v1.json`、
`local-policies-v1.json` 和已有 build/release receipts，形成唯一可核对的分发组合投影。
具体可机读 schema 由窄合同任务确认；此文不声称已有万能发布清单或签名更新器。
组合需要关联 Mod、工作台/依赖、Runtime/Evidence、可选模型包、支持平台/游戏版本、
Hub API/数据协议、下载位置、内容摘要和回滚条件。已观察运行版本与目标版本分开显示。

各组件不必用相同版本号，也不因无关源码提交一起重建。匹配的是兼容合同和经过验证的
产物，不是用户盲目下载每个组件的 latest。程序只能接受固定可信发布者和允许来源；
摘要验证完整性，可信发布通道/签名用于来源信任，二者不能混称。

### 发布顺序和客户端体验

1. 审查源码/测试，构建固定候选并保留产物身份；不要每个成员本机拉 main 后随意编译。
2. 涉及 Hub 的更新，由操作者做备份、迁移/兼容测试、部署与实际 health/producer 核对。
   先证明本批所需新旧客户端组合可用，不事先宣称所有旧版本都兼容。
3. 完成本批实际安装/冷加载/工作台/模型链验收，再更新推荐组合和授权的 Workshop 发布。
4. Mod 启动时检查已加载自身与本机组件/Hub 的实际兼容性；缺少部分自动准备并显示步骤。
   兼容旧组件不用重装；不兼容则显示具体原因和修复操作，保留人工控制/可用本地功能。
5. 新组件先下载、核验和并存准备，在无在途模型提交、相关任务允许的安全边界启用。
   需要重开游戏时显示“已准备，重开后生效”；不会在一局中替换已加载 DLL 或训练依赖。
6. 失败保留旧可用组合、数据、模型、队列、同意和日志。数据迁移单独验收；回滚代码
   不能靠恢复旧数据库抹掉最新权限/用途记录。

“版本结合”指共同发布批次、兼容检查、一次更新入口和明确运行状态；
不是每次成员订阅/更新 Mod 就部署一次共享 Hub。管理员只管理一台团队服务；
用户界面显示团队服务状态，普通成员没有生产部署按钮。
允许本机工作台自身查看兼容更新，不强迫所有更新都必须重新上传不变的 Mod。

## 6. 推进顺序与 1b 并行边界

先完成 1a-00，只读核对本机最新进度、writer 和在跑任务。然后按事实选择下一张卡：

- 1a-01/02：修好既有 Runtime 交付/加载/暂停/停止/恢复，不先重训模型。
- 1a-04：在既有应用上定义最小“配置本机”操作合同及统一授权范围；复用现有 owner。
  把组件准备、账号/设备连接和采集许可编排分别做成小实现卡，不一次重写所有服务。
- 分发验证：一个目标平台、干净机器、固定 Mod/工作台组合；验证少量点击完成配置、
  二次启动无重复登记和重复同意、断网/中断可恢复。首先证明一条真实链再扩平台。
- 1a-05/06：游戏内选择模型→加载接管→暂停/结束→报告，复用同一状态和设置结果。
- 1a-03/07 与 08–12：按矩阵补齐四模型全场景；并行补采集/数据集/本机训练/分析页。
  同一 writer 不跨多张耦合卡同时改公共合同；默认一个实现任务，可并行独立只读审计。
- 1a-13：真实成员安装、核心完整用户旅程、失败恢复和四模型全场景验收。
  好看不是完成，纯命令行能跑也不是完整产品；高级图表/商业化能力不阻塞签收。

1b 可以同步做数据盘点、覆盖/长度分析、成本方案和无消费的云适配设计。
固定准入与训练/恢复/导出路径稳定后，可另发一张明确预算和数据范围的云端小 profile 卡；
其执行须独立授权，属于提前验证，不冒充 1a 完成或整批规模训练。正式把主线转向 1b，
仍须 1a 的核心工作台、简单配置、四模型目标全场景、安全控制、数据到模型链和恢复签收。
不等待所有视觉打磨，不借 1b 名义放弃这些核心交付。没有本轮新增云计算授权。
