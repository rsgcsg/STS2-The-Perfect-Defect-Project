# P1 协议规格（v2 草案）

状态：2026-10-14 草案，等调查任务 C 的逐场景事实补齐后定稿。名字一直叫 P1，内容按版本演进。
上级：[SYSTEM_MAP 第 3 节](../SYSTEM_MAP.zh-CN.md#3-环境协议p1)。

## 1. 一套协议包含什么

P1 是从 Host 到 Agent 的一整套约定，分三部分：

```text
Host（Reference 或 Managed） ←[P1-H：向 Host 要什么、怎么交互]→ P1 适配器 ←[P1-A：Agent 看什么、做什么]→ Agent
```

| 部分 | 内容 | 对谁统一 |
| --- | --- | --- |
| P1-A（Agent 面） | 观察里有什么、动作目录是什么、每步得到什么反馈、一局怎么开始和结束、出错怎么表达 | 所有 Host、所有 Agent 完全相同 |
| P1-H（Host 面） | 适配器从 Host 取哪些事实、用什么接口取、怎么下发动作、怎么拿回执 | 每种 Host 一份实现 |
| 适配器 | 把 P1-H 取到的东西组装成 P1-A 的观察；把 Agent 选的动作交给 Host；检查完整性、处理等待和失败 | 每种 Host 一个，行为必须符合 P1-A |

Agent 只认识 P1-A。"Read""snapshot""controller lease"这些都是 P1-H 和适配器内部的事，Agent 看不到，也不需要知道。

**两个 Host 在 P1 下等价**，指的是：对同一个游戏状态和同一串动作，两边的适配器给出完全相同的 P1-A 观察、动作目录和反馈
（只允许声明过的绑定 ID 不同），并且都通过同一套 P1 一致性检查。规则本身由同一个 `sts2.dll` 保证相同。
验证方法见 [SYSTEM_MAP 第 5 节](../SYSTEM_MAP.zh-CN.md#5-改哪一层以及两个-host-怎样算等同)。

## 2. 设计原则

1. **信息**：每个决策点给出玩家此刻通过"纯查看"能知道的全部信息。纯查看 = 不揭示新的随机内容、不改变游戏状态、可以撤回。
   打开一个还没打开的奖励组、宝箱、事件下一页都是揭示，不算纯查看，不能提前给。
2. **动作**：保留游戏真实的选择阶段（选牌→目标→确认/取消；奖励的打开/领取/离开；卡牌奖励的选择/跳过/返回）。
   只省略滚动、坐标、悬停这类设备步骤。合并阶段要逐机制证明不丢信息、不改效果、不少选择机会，并升版本。
3. **时机**：Agent 只在"稳定决策点"被调用——当前有完整合法目录、页面不在结算中。等待、动画、结算由适配器处理，Agent 看不到。
4. **不加提示**：不放程序推导的东西（访问计数、推荐、步数）。区分"第一次来"和"重访"是 Agent 记忆的事。
5. **完整才发布**：必需信息缺一项，这个观察就不发布，适配器报告缺什么；不给半个观察。
6. **公平**：隐藏 RNG、真实抽牌顺序、未来奖励永远不进观察。

P1 不保证马尔可夫：同一个观察可以出现两次而需要不同决定，所以默认 Agent 要有记忆。

## 3. P1-A：观察

每个决策点一份 JSON 文档，schema `sts2.p1/observation-2`。字段分"模型可见"和"信封"两类，信封只用于绑定动作，不进模型。

| 部分 | 内容 | 何时出现 |
| --- | --- | --- |
| `run` | 角色、进阶、幕、层、Boss、修饰、HP/最大 HP、金币 | 总是 |
| `deck` | 牌组（多重集），每张卡：definition_id、名称、升级、费用、描述文本、数值字段 | 总是 |
| `relics` / `potions` | 每个：definition_id、名称、描述、计数器；药水槽上限 | 总是 |
| `map` | 本幕地图：节点类型、连线、当前位置、已走路径 | 总是（待 C 确认非地图页时也可查看） |
| `screen` | 当前决策页面：类型、页面上的全部内容（奖励列表、事件文字与选项、商店货架、营火选项、选择器候选与已选状态等） | 总是 |
| `combat` | 回合、能量、玩家格挡/能力/充能球/姿态；手牌（当前费用、可否打出）；抽牌堆（多重集，无顺序）、弃牌堆、消耗堆；敌人（HP、格挡、能力、意图与数值） | 战斗中 |
| `completeness` | 已声明可缺字段的缺失清单（必需字段缺失时不发布） | 总是 |
| 信封 | observation_id、episode_id、动作绑定 ID、Host 与游戏版本 | 总是，不进模型 |

实体之间用观察内的引用连接（例如动作的目标指向 `combat.enemies[i]`）。引用 ID 每个观察内稳定，不跨观察承诺。

## 4. P1-A：动作、反馈和一局的边界

- **动作目录**：当前决策点的全部合法动作，每个：动词、引用参数（手牌、目标、选项、地图节点、商品……）、可读标签、信封里的绑定 ID。
  目录由游戏/Connector 产生，适配器和 Agent 都不增删。
- **一步**：Agent 选一个动作 → 适配器下发 → 返回 `delivered` / `not_delivered` / `unknown`，以及下一个稳定观察。
  `not_delivered`（例如状态已变）时适配器给新观察，让 Agent 重新选；`unknown` 时本局以删失结束，不重试。
- **一局**：由任务（角色、进阶、种子）开始，到胜/负总结页结束；超步数、超时、unknown、不完整观察算删失并记录原因。
  开局、种子、重开属于任务管理，不是 Agent 的动作。

## 5. P1-H：各 Host 怎么实现

| Host | 取事实 | 下发动作 | 现状 |
| --- | --- | --- | --- |
| Reference（真实游戏 + Mod） | Connector `snapshot-1` + 当前声明的全部 Reads（`run_deck`、`combat_piles`、`shop_catalog`、`surface_card`），同一快照内组装 | Connector actions + receipts，执行前复验 | 能用；地图在非地图页、部分详情待补 |
| Managed Exact（同一 `sts2.dll`，无渲染） | 从游戏模型状态直接投影（`managed-player-environment.mjs`，信息策略 `player_visible_v1`） | Managed 绑定动作，同样的回执语义 | 部分场景、部分目标类型不支持 |

## 6. 版本

| 版本 | 内容 | 数据 |
| --- | --- | --- |
| P1 v1 | 适配器把 `snapshot-1` + 当时声明的全部 Reads 组装成一份观察，字段沿用旧结构 | 旧 Human 录制（H Snapshot1 + 录到的 Reads）就是 v1 数据，缺的 Read 显式标记 |
| P1 v2 | 本文的统一观察文档、地图常驻、完整才发布、一致性检查 | v1 数据可转换为 v2，v2 新增而 v1 没录到的字段标为缺失 |

## 7. 一致性检查（每个 Host 适配器都要过）

1. 观察文档符合 schema，必需字段齐全，不含隐藏信息字段。
2. 目录完整：与 Host 原生目录逐项对应，执行前复验生效。
3. 回执三态语义正确，unknown 不重试。
4. 同一种子、同一动作序列下，两个 Host 的观察和目录相同（成对差分）。
