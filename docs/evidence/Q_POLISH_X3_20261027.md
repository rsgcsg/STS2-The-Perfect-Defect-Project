## 原因与实现

Q3、X2曾因 `maintenance status` 超时而改读持久文件；Q2已修视图故障隔离和停用可见性，本次复用这些owner，不另建入库或状态账本。原GET调用完整 `importer.status()`，既等维护器长时间持有的锁，也准备无关恢复状态。现只投影维护信息，锁最多等50ms；忙时HTTP/CLI明确 `busy / 在忙，稍后再查`，队列暂未核实，不写成unknown、停用或0。只有首次GET的读取超时被映射busy；控制POST无自动重试。

原维护器每tick先观察退出，但版本盘点/原件查找后可能已开游戏；每个新打包、保全、派生、冷却、缓存整理、盘点准备和正式盘点前重新读原Catalog。被挡住的首次pack不留未发生的active；被挡的cache-trim不提前写“已派发”签名。已经运行的单步按原验证完成，下一步再等退出；页面与固定HTML从同一操作投影当前cache-trim，显示“正在整理缓存”，盘点开始也先发布状态。

原单步没有协作暂停入口；不通过强杀制造unknown，也不为暂停改写Store完整验证。未降整个Workbench进程优先级，因为录制控制/查询共用同一进程，整体降级会一起拖慢它们。该门是最新观察后准入，不是与外部游戏启动的原子互锁，不能保证所有场景零卡顿。

## 验证与量化边界

相关74项回归通过：真实Store/原封存夹具的入库→保全→完整读回及持久重开；首次pack、preserve、derive、cool、cache-trim及盘点签名后开局反例；进行中的cache单步仍完成、下步不派；真实HTTP→CLI busy JSON及页面；原unknown、缓存完整验证、近两局保护和活跃reader保持。游戏观察是受控替身；不冒充开过游戏或真人新录制。

资源短测使用未修改的生产 `trim_cache` 与真实本地Store/独立本地peer，4份各32MiB合成数据，保留最近2份：128MiB→64MiB，回收8块/64MiB；wall 0.2287秒、线程CPU 0.2204秒（平均约96.4%单核）；peer逻辑读128MiB+元数据，临删除本地比较读64MiB，合计约192MiB逻辑读取。暖文件缓存的kernel输入/输出块计数均0，不把它说成物理磁盘零IO、R2网络或真实游戏帧时。后续实际cache操作在原operation/maintenance记录wall、thread CPU与回收字节，不改变trim收据/校验。

完整候选按原 `npm run check:plan -- --base origin/develop --run` 选门；closeout/diff、非作者复核和准确head CI分别保留原收据。测试失败只修本次真实原因：旧视图测试绕过_tick且未提供游戏观察，补明确stopped Catalog；旧异步cache测试曾竞争完成状态，改用事件同步真实worker，保原断言。CLI既有main把BoundaryError序列化，回归按真实JSON/exit code验证。
