## One explicit profile across the existing owners

Connector already owns the complete finite v2 menu and card/target selection.
SDK rc.5 adds the corresponding strict REST client methods. Policy Runtime
rc.13 dispatches the manifest's exact snapshot profile through capabilities,
atomic context, stateful port-2, submit and successor. It does not learn STPD
model architecture or create native operands. Text selection remains a text
interaction; only a confirmed native result counts as native delivery.

The research adapter uses closed `stpd/m2-policy-config-v2`, explicit
`text-menu-v2`, and adapter version 2.0.0. Old configuration and default calls
remain v1. The portable export is validated against the exact manifest digest
on the same read that loads its payload. An independently valid replacement
package with the same model ID is not interchangeable with the pinned bytes.
Repeated observations retain the existing one-write memory/cache rule.

Workbench derives v2 M2/Reset recipes from the validated source, projection and
training-input lineage, never from a mutable display label. The ordinary purpose
ledger, training worker, export receipt and registration owner remain in use.
A Managed engineering source is not promoted to Human demonstrations, and test
purpose does not authorize training. Registration uses a distinct
`text-menu-m2-v2` private Runtime profile and checks actual installed SDK/context
and Runtime manifest support. There is no fallback to the v1 pin.

Explicit preparation/CLI installation uses the existing installer. Required v2
SDK checks occur after exact temporary-stage verification and before replacing
an old installation. Rejection preserves old installed bytes and its receipt.
No released kit currently inventories this candidate v2 asset: the temporary

## Evidence consistency and review corrections

Evidence rc.21 consumes the exact v2 snapshots/results and bound complete menu.
It rejects generic Receipt/Successor events mixed into text runs, including an
unknown native result followed by a forged delivered record. Dispatch counts
must match the selected action domain and the actual cumulative budget.

The budget verifier follows the Runtime producer: initial Auto may have no
mode-change event; Shadow shares an autonomy budget but never submits;
Human, One-Step completion, failure and exhaustion hand off control. A new
explicit active mode is required before later dispatch. Exhaustion itself is
the handoff event; the verifier does not invent a missing Human event.

Independent review reproduced the original resealed contradictions, then found
initial-mode, exhaustion and Shadow boundary errors in an intermediate fix.
Final regressions distinguish legitimate restart from forged resets and reject
dispatch after handoff without new activation. The final component suite has
168 passing tests. A historical v1 archive still verifies with 107 events and
unchanged content ID
`f97a29bb5725ffc3a05f699eab24d395741dbc6cb3fe6b877e00ee7389b081a6`.
