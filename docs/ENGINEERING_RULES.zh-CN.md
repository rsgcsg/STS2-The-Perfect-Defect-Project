## 1. 目标、评测与能力记分板

目标是能稳定、连续地玩真实 STS2，并且不断变强，同时保持易理解、易修改、易验证。
能力进展看 [SCOREBOARD](SCOREBOARD.md)；当前选择和下一步看 [CURRENT](memory/CURRENT.md)；已实现、可用的组合与证据看 [STATUS](STATUS.md)。
PR 数、测试数、文档篇幅和 receipt 都不算能力进展；可靠性、维护成本和交付等待单独看，不压进胜率。
首批薄片是 Defect A0；原完整 G2/V1 与 Stage1a 的其他角色、难度和功能范围仍保留，改变范围要用户明确裁定。

**种子套件**（种子由 `python/stpd/game_seed.py` 的 `derive_game_seed("<套件名>", 序号)` 生成，绑定游戏版本）：

| 套件 | 局数 | Host | 用途 |
| --- | --- | --- | --- |
| `smoke-20` | 20 | Managed | 改动后的快速检查 |
| `dev-500` | 500 | Managed | 日常迭代与对比 |
| `test-1000` | 1000 | Managed | 留出集，只在声明达到某一阶时跑，不用于调参 |
| `ref-20` | 20 | Reference（真实游戏） | 检查 Managed 结果在真实游戏上是否成立 |
| `gen-<角色>-200` | 每角色 200 | Managed | 泛化：没训练过的角色 |

- 种子由套件名派生，不同套件的同一序号不是同一种子。比较两个 Host 时必须用**同一个** seed manifest。
- 训练和数据采集不得使用任何套件种子（评测工具维护黑名单）。
- `dev-500` 可以用于有记录的模型选择（记录曝光）；`test-1000` 隔离，每次开封记录用途和结果，不用于调参。
- 游戏更新后套件按新版本重跑，新旧版本结果分列。
- 每次评测报告完整分母：计划局数、开始、自然终局（胜/负）、删失（按原因）、unknown、未恢复卡死。删失不算胜，也不从分母里去掉。

**能力阶梯**（数字一律来自评测工具，附 eval id）：

| 阶 | 达成条件 |
| --- | --- |
| L0 环境稳定 | Managed：随机合法策略跑 `dev-500`，完整分母报告，自然终局 ≥ 95%（提案，待用户确认），unknown 0，未恢复卡死 0。Reference：`ref-20` 全部到达自然终局，清理状态无 unknown。已发布目录必须完整，另报支持覆盖率 |
| L1 基线可测 | 随机合法与一个已有 Agent 在 `dev-500` 上有层数分布、到达幕数和胜率（Wilson 95% CI）；同一 `ref-20` manifest 两个 Host 成对运行，报告首个分叉和结果差异（不作为等价判定）。旧模型按它自己的输入 profile 单列 |
| L2 过第一幕 | `dev-500` 中位数到达第二幕 |
| L3 能赢 | `test-1000` 胜率 ≥ 5%，且 CI 下限 > 2% |
| L4 暂定工程目标 | `test-1000` 胜率 ≥ 15%（与人类水平的对应关系未验证） |
| L5 往上爬 | 更高进阶、更多角色、泛化套件达标；到时再细分 |

每项工作在开始时写一句：推进哪一阶的哪个数字、消除哪个风险，或服务活动计划里的哪项交付。三者都不是的工作默认不做，
除非是 30 分钟内能完成的小修。**基础设施工作采用拉动式**：由实际观察到的阻塞（附 run/eval id）或活动计划里的交付启动；
不为假想的未来组合预先建设。已经做好的基础设施优先复用。

## 2. 按风险分三档

判断依据是**改动碰到了什么不变量**，路径只是默认提示。碰到下面任一不变量就按 T1 处理，不管文件在哪。

**T1 硬核不变量**（保持严格）：

1. STS2 拥有规则、RNG、原生合法性与 Commit；不读取隐藏状态，不做坐标/反射式输入。
2. Connector 发布完整有限的合法动作目录并在执行前复验；消费者不自建合法性、不构造原生操作数。
3. 回执区分 delivered / not_delivered / unknown；**unknown 永不自动重试**。
4. Agent 只得到声明过的公平公开信息；特权信息只能进训练标签，不能进学生输入。
5. 原始录制不可变、来源可追溯；不覆盖、不重写、不删除失败记录。
6. 不提交游戏文件、反编译源码、原始 Human 数据、权重、凭据或 `.local/`。
7. 发布给他人的安装产物（Mod/Runtime/Host 包）有确切版本和回滚。

下列**行为**无论文件在哪都按 T1 审查：P1 公平信息与动作目录、Stop/预算/unknown 处理、数据用途与凭据、远端执行生命周期、
发布产物。纯指标、数值优化和文档编辑按 T2。

| 档 | 默认路径（只是提示） | 流程 |
| --- | --- | --- |
| T1 | `components/`、`apps/game-mod`、`contracts/`、`platform-bom.json`、原始录制与 Store 写入路径 | topic 分支→独立审查→所属测试与选定 CI→normal merge；改原生代码另跑本机 exact-game 门；组件源身份照常更新，产物版本只在发布时变 |
| T2 | `python/stpd`、`python/spireagent`、`python/deploy`、`apps/ingame-ui`、`apps/workbench`、`tools/`、`docs/` | topic 分支→作者自查清单→`check:plan` 选定的 CI 通过即可合并；不写证据阶梯段落 |
| T3 | `experiments/<日期>-<名字>/` | 不审查、不进 CI；T1/T2 代码不得 import 它；想长期保留就提 PR 升到 T2 |

三个维度互相独立，不能混为一谈：
- **审查强度**（T1/T2/T3）：按上面的行为判断。
- **组件源身份**：BOM 里的 source revision 等由 `check-platform-bom` 对所有组件（含 Workbench、Live UI）机械核对，改到组件源码就要更新，与档位无关。
- **产物版本**：只在发布安装产物时变。
CI 选哪些检查仍由 `check:plan` 按路径决定，档位不改变 CI 选择。合并方式：改到 `components/` 或 `apps/` 用 normal merge，其余可以 squash。

T2 自查清单（PR 里打勾即可）：做了什么、怎么验证（命令或 run id）、会影响谁、怎么回滚。

**任何设计或实现都先过这四步**（不论是新增、恢复历史组件还是改协议）：

1. 先查历史：[DOCUMENT_MAP](DOCUMENT_MAP.md)、`docs/design/`、ADR、`docs/archive/`、相关 PR。找到的方案可以不用，但要说明为什么。
2. 放进 [SYSTEM_MAP](SYSTEM_MAP.zh-CN.md) 的哪一层、是哪个组件或哪个协议版本。
3. 检查它是否符合那一层"必须统一"的内容；符合就在该层内实现。
4. 不符合时，先改上层（ADR，写明取舍和迁移），再改下层。不允许在下层另起一条平行链路。

**测试分六类，各自证明不同的事**：

| 类型 | 证明什么 | 什么时候跑 |
| --- | --- | --- |
| 单元/合同测试 | 代码按约定工作 | 每次提交，CI |
| 协议一致性检查 | 某个 Host 符合某个协议版本 | 改 Connector、Managed 投影或协议时 |
| 成对差分 | 两个 Host 在声明范围内的首个分叉（SYSTEM_MAP 第 5 节） | 改 Host、投影或游戏版本变化时 |
| 原生场景测试 | 真实游戏里某个机制能跑通 | 改原生代码时，本机 exact-game 门 |
| 评测套件 | Agent 的能力（第 1 节） | 每个候选模型/Agent，每次声明进阶 |
| 长跑 | 长时间稳定、无泄漏 | 发布前或怀疑稳定性时 |

T1 保持现有要求；T2 只给有逻辑的模块写单测，每条流水线留一个端到端冒烟；T3 不要求。
新增测试必须能抓到真实出过或可能出的错，不为镜像文档写测试。下层测试通过不代表上层成立：
CI 绿不等于游戏里能跑，游戏里能跑不等于有能力，这些只用对应类型的测试回答。

## 3. 研究的运行、数据和评测怎么管

研究改动默认属于 T2/T3，可以自由改模型、Input、loss、数据选择和超参，只要写进 run 的 config。
需要用户批准的只有第 6 节列出的事项。

**一次训练或评测 = 一个 run 目录**（放在私有 `.local/runs/` 或团队存储，不进 Git）：

```text
runs/2026-10-20-bc-p1-a1b2c3/
  config.yaml        # 全部超参、模型结构、数据集名@哈希、种子
  meta.json          # git SHA、是否有未提交改动、机器/设备、开始结束时间
  metrics.jsonl      # 训练曲线
  ckpt/              # checkpoint；最终模型另存 model.pt + model.json
  eval/<suite>.json  # 评测结果
  notes.md           # ≤ 10 行：目的、结论、下一步
```

**数据**：原始录制保持现有不可变 Store（T1）。训练用的派生数据集是只读快照，带 manifest
（来源记录 ID、投影版本、行数、过滤规则、来源类型）。派生数据可以随时重建或删除，原件不受影响。
来源分"轨迹"和"标注"两类，见 [SYSTEM_MAP 第 4 节](SYSTEM_MAP.zh-CN.md#4-数据来源在框架里怎么放)。

**原件与训练数据不同**：原件是底片，数据集是为某个用途挑选和加工的结果。用途、划分和曝光由 Curation 记录；
没捕获的事实不回填，推断出的标签作为声明了假设的研究配方。

**训练放在哪里**：超过 1000 次实际参数更新的训练默认在远端 GPU 上跑；本机 CPU 只做 ≤ 1000 步的冒烟、机制检查和调试。
机制检查用可辨识的连续小集（同一可见输入和历史不对应冲突标签），并列出别名和未拟合的样本；不要求任意小集的损失降到 0。

**完整配置说明**：每次提出一个训练或 Agent 配置给用户确认时，必须写全这十项，缺一项不算完整：

1. Agent 怎么接协议：每一步的数据流、两种 Host 上的具体路径、什么不进模型。
2. Agent 内部组件：输入投影、模型、选择规则、记忆管理、输入上限。
3. 模型结构：每一部分的配置、计算顺序、参数量，以及为什么。
4. 数据：内容、来源、数量、目标、排除规则、缺失处理、划分、序列切分、存储格式。
5. 损失函数：公式和每一项的权重、哪些样本计入。
6. 优化与时间表：优化器、学习率、裁剪、截断反传、批大小、轮数、步数估计、检查点、种子。
7. 计算与预算：设备、本机与远端的分工、时间与费用估计。
8. 评测与验收：指标、套件、对照组、预期结果。
9. 风险与待核事实（标明哪些是推断）。
10. 与上一版配置的区别。

**评测输出**：局数、胜率及 Wilson 95% CI、平均/中位到达层、到达幕数分布、卡死/unknown/删失次数、
决策/秒、Agent 与模型版本、Host 与游戏版本。单局、单种子、训练 loss 只能写在 run 的 notes 里。

## 4. 证据只分三级

| 级别 | 写法示例 |
| --- | --- |
| 代码检查过 | “单测 + CI 通过，commit abc12345” |
| 真实跑过 | “在 Reference/Managed 跑过，run id …” |
| 指标结论 | “dev-500 胜率 3%（2–5%），eval id …” |

只写达到的那一级，不写“不证明什么”的清单。失败与原始记录靠不删除 run 和录制来保留，不靠文字账本。

## 5. 文档怎么写

- 文档分四级，下级写明自己落实的是上级哪一节：
  1. 顶层：[SYSTEM_MAP](SYSTEM_MAP.zh-CN.md) 和本文件。
  2. 分层架构：[ARCHITECTURE](ARCHITECTURE.md)、[COMPONENTS](COMPONENTS.md)、ADR。
  3. 组件与协议规格：各组件 `docs/`、协议文档。
  4. 有日期的东西：计划、证据、日志、讨论。它们可以过期、归档，但不删除；归档目录有索引，能按日期和主题查到。
- 预算：`AGENTS.md` ≤ 120 行；`CURRENT.md` ≤ 4 KB，大白话；单个规范文档 ≤ 300 行，超出就拆分或删减。
- 一个事实只写一处，其他地方链接过去。
- 数字和单位、单词之间要有空格；哈希最多写 8 位（机器文件除外）；先写结论再写细节。
- “限制/未做”最多一行。禁止成段的免责、非声明、“这不等于……”列举。
- 规范文档只写“现在怎么做”。历史过程写进 `docs/log/YYYY-MM.md`，每条 ≤ 3 行，只追加。
- 计划文档超过两周没更新时复查：仍有效、被替代（加链接）、或归档（移动，不删除）；不按年龄自动移动。
- 每轮工作结束的报告用下面的模板，不另写长篇 closeout：

```text
目标：推进哪个能力数字 / 消除哪个 T1 风险
完成：……（commit / run / eval id）
结果：数字变化，或“无变化”
失败与原因：……
下一步：……
需要用户决定：……（没有就写“无”）
```

## 6. 角色与决策权

| 角色 | 负责 |
| --- | --- |
| 用户 | 目标与优先级、Agent 偏好、能力阶梯与套件定义、下表"由用户决定"的事项 |
| 计划与集成 owner（当前由 Claude 担任） | 系统地图与规范、当前组合与任务、审查 PR 与结果、维护 CURRENT/SCOREBOARD/DECISIONS 的真实性、提出反对意见 |
| 实施与独立审查（当前由本地 Codex 担任） | 独立调查、审计、核对、评估方案、提出自己的意见；按任务实现、跑测试/游戏/训练、开 PR；主管审查通过且 CI 绿后合并 |

角色不绑定具体模型。作者不能独立验收自己写的关键治理规则或公共契约，需要另一个角色审查。

| 由用户决定 | 由主管或实施 Agent 自行决定（并在 DECISIONS 记一行） |
| --- | --- |
| 能力目标、阶梯和评测套件定义 | T2/T3 的所有实现与研究选择 |
| 环境协议的信息范围和动作粒度（协议规格） | 协议规格内的实现 |
| 修改 T1 不变量本身 | 在 T1 不变量内的修复 |
| 花钱（GPU、LLM API）超过已批预算 | 已批预算内的花费 |
| 删除原始数据、关闭历史 PR、发布 release、生产部署 | 普通 develop 集成 |
| 替换“推荐/默认 Agent” | 训练新模型、跑评测 |
| 冻结开关期间的模型方案变更 | 冻结关闭时的模型方案变更 |

**冻结开关**写在 [CURRENT](memory/CURRENT.md) 第一行（`模型方案冻结：开/关`）。冻结对象：首轮训练配置和任何新模型方案
（含实验性的）的结构、Input、Target、数据选择、训练配置和预算。开启时这些要先得到用户确认；工程实现、数值后端、
≤ 1000 步的机制检查和已批预算内的路径冒烟不受冻结限制。关闭由用户在 DECISIONS 记一行。
`docs/DECISIONS.md` 每条一行：日期、决定、理由、谁定的、状态。

## 7. 任务包与协作

**本地 Agent 不只是实施者。** 它额度充足、能直接访问代码、数据、本机环境和历史，适合承担：

- 主管不确定、需要仔细查证的事实（代码行为、数据计数、历史原因、运行结果）；
- 对规则、架构、协议、计划、配置、主管自己的结论做独立审查，可以从不同方向分别审；
- 方案评估、替代方案、根因分析、深度讨论；它可以不受现有设计约束，主动提出自己的意见；
- 任何实现、测试、运行和训练任务。

主管应优先把需要大量阅读或验证的工作交给本地 Agent，自己负责提问、综合、裁决和维护文档的真实性。
本地 Agent 可以读交接文件夹里的会话记录和简报，了解用户原话和主管做过的判断。

**新计划先独立审计，然后按授权推进。** 流程：

1. 主管把计划或配置的完整内容写进仓库（或交接文件夹）的一个文件。
2. 本地 Agent 独立审计：对照代码、数据和历史核实，指出错误、遗漏和更好的做法，写到交接文件夹 `replies/`。
3. 主管逐条回复"接受 / 反驳（附证据）/ 需再查"，把接受的结论改进对应的 owner 文档，写明修订后的 head。
4. 事实矛盾必须解决；取舍分歧由有权角色裁定并记录异议，不要求所有分歧消失。
5. 已授权范围内直接实施。只有实质改变目标、协议规格、冻结对象、预算或涉及破坏性操作时，才回到用户确认。

交接时写明：任务、读的是哪个版本（head 或文件日期）、做了/没做、证据、剩余问题、下一 owner。
"收到文件、读过、接受、已实施"是四件不同的事。

主管给实施 Agent 的任务包可以很明确，也可以只给目标让它先调查；但都要有下面几项：

```text
目标（推进哪个数字 / 消除哪个风险）：
背景与入口（相关文件、已有组件，优先复用什么）：
要做的事（明确的步骤，或"先调查再提方案"）：
不要做的事：
验收（命令、套件、期望数字或产物）：
停止条件（遇到什么就停下来汇报）：
档位与合并方式：
```

- 同时最多 2 个写代码的 worker，同时活跃的可写工作槽最多 5 个；共享接口同一时间只有一个 writer。
  历史 worktree、分支和 PR 不按年龄删除：先核实唯一增量、未提交内容和数据/运行依赖，再经用户批准处置。
- 一个任务一个分支一个 worktree；不共用写分支；不 direct-push `main`/`develop`；不 force-push。
- T1 改动必须经主管审查；T2 改动作者自查，主管抽查。
- 不无限等待 CI 或外部任务：超过 30 分钟就交接，写明下一步该看什么。
- 不手改 SCOREBOARD 里的数字，只粘贴评测工具的输出并附 eval id。
- 任何“做到了”的说法都要附 commit、run 或 eval id。

## 8. 迁移

本规则合并后文案即生效；组件源身份、BOM 核对、normal merge 照旧（第 2 节）。G0–G6 分级、证据阶梯、closeout 只用于 T1 审查。
旧 owner 规范中与本文件直接冲突的条款，在同一轮的入口切换 PR 里逐条修改（见活动计划）；其余大文档修改时顺手收敛。
尚未实施、不能用文案宣布已生效的机制：套件执行器与 SCOREBOARD 自动生成、T1 行为的 CI 标记检查、CI 排除 `experiments/`、
冻结批准的机械绑定、历史资产处置。
